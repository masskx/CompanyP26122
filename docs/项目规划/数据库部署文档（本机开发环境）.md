## 1. 部署总览

### 1.1 三个库的职责

后端 `backend/app/` 对三个库的分工是固定的，部署时不要混用：

| 数据库 | 在项目中的职责 | 关键代码位置 | 不做的事 |
| --- | --- | --- | --- |
| **openGauss** | 会话与消息、工单副本、报告记录 | `app/db/`、`app/db/migrations/*.sql` | 不存设备时序 |
| **Apache IoTDB** | 设备/测点原始时序、MQTT 消费水位线 | `app/timeseries/`、`app/ingestion/` | 不存会话和向量 |
| **Milvus** | 知识库切片向量与检索索引 | `app/rag/`（`store.py`、`retriever.py`） | 不存原文（原文在语料目录） |

### 2.2 开工前逐项检查

```powershell
# 1) Docker 是否在跑、分配了多少资源
docker version
docker info --format '{{.MemTotal}} {{.NCPU}} {{.OperatingSystem}}'

# 2) WSL2 发行版
wsl.exe -l -v

# 3) 端口占用（三个库的主机端口都应该为空闲）
foreach ($p in 5432,6667,19530,9091,9000,9001) {
  $t = Test-NetConnection 127.0.0.1 -Port $p -InformationLevel Quiet -WarningAction SilentlyContinue
  "$p = $t"
}

# 4) 已被占用的端口是谁
Get-NetTCPConnection -LocalPort 5432 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalAddress,LocalPort,OwningProcess
```

判定标准：`docker info` 的 `MemTotal` 至少 12GB；`wsl -l -v` 状态为 `Running` 或可启动；
第 3 步中 `5432/6667/19530/9091` 应为 `False`（部署前）。

### 2.3 镜像加速（国内网络必须处理）

本机实测 **Docker Hub（`registry-1.docker.io`）直连超时**，而 `quay.io` 可达。
处理方式是"从加速站拉取 + 重打成官方标签"，**不改 compose 里的镜像名**，这样编排文件与
官方文档保持一致：

```powershell
# Milvus 主镜像
docker pull docker.m.daocloud.io/milvusdb/milvus:v3.0.5
docker tag  docker.m.daocloud.io/milvusdb/milvus:v3.0.5 milvusdb/milvus:v3.0.5

# openGauss 镜像（本次走 1ms 加速站，enmotech 第三方镜像）
docker pull docker.1ms.run/enmotech/opengauss:6.0.0
```

注意点：

1. **标签必须打回官方名**，否则 `docker compose` 每次都会去 Docker Hub 重新拉取。
2. `quay.io/coreos/etcd`、`milvusdb/minio` 这两个镜像实测可直连；若同样超时，用同样的
   `pull → tag` 方式从加速站替换。
3. 如果长期在本机开发，建议在 Docker Desktop 的 `daemon.json` 里配置 `registry-mirrors`；
   但**修改后需要重启 Docker**，会中断其他正在运行的容器（本机还有 dataease 等），
   因此本次没有自动修改，只按镜像维度处理。
4. 加速站仅解决"拉不到"的问题，不改变镜像内容；生产仍应固定镜像 digest（见 8.2）。

### 2.4 目录与路径规划

| 用途 | 路径 | 说明 |
| --- | --- | --- |
| openGauss 编排 | `D:\工作目录\opengauss` | 含 `docker-compose.yml`、`init\*.sql`、`README.md` |
| IoTDB 安装与脚本 | `D:\工作目录\iotdb_install` | Windows 侧启停脚本；实际安装在 WSL 内 `~/iotdb` |
| Milvus 编排与数据 | `C:\milvus` | 含官方 `docker-compose.yml`、`override`、`volumes\` |

**为什么 Milvus 放在 `C:\milvus` 而不是中文目录**：Compose 把宿主机目录绑定挂载进容器时，
中文路径容易在某些工具链/驱动上出问题。本次 Milvus 的 `volumes\` 是真实绑定挂载到
`/var/lib/milvus` 等路径的，因此刻意选纯英文短路径。openGauss 用的是 **Docker 命名卷**
（不走 Windows 绑定挂载），所以放在 `D:\工作目录` 下没有影响。

## 3. openGauss 部署（会话存储 / 工单副本）

### 3.1 为什么选这个形态

- 后端 `app/db/migrate.py` 会检查数据库的 `datcompatibility`，**必须是 `PG`**，
  否则抛出 `CompatibilityError`（`A` 兼容模式下空字符串会变 NULL，会让业务语义出错）。
- `openGauss` 兼容 PostgreSQL 协议，后端用 `psycopg`（PG 驱动）直连，不需要 openGauss 专属驱动。
- 本项目只存会话、消息、工单副本、报告记录这类小数据量，单实例 + 命名卷足够。

> 本次使用的是 `enmotech/opengauss` 第三方镜像（`6.0.0`），不是官方 `opengauss/opengauss-server`。
> 两者启动参数（`GS_PASSWORD`、`GS_PORT` 等）基本一致；官方仓另有 `7.0.0-RC3.B025`（见 1.4）。

### 3.2 镜像与版本

```powershell
docker pull docker.1ms.run/enmotech/opengauss:6.0.0
docker images | Select-String opengauss
```

实测版本：`openGauss 6.0.0 build aee4abd5`，`x86_64`。

### 3.3 编排文件（逐字）

`D:\工作目录\opengauss\docker-compose.yml`：

```yaml
name: opengauss

services:
  opengauss:
    image: docker.1ms.run/enmotech/opengauss:6.0.0
    container_name: opengauss
    hostname: opengauss
    privileged: true
    restart: unless-stopped
    environment:
      # 超级用户 omm 的口令，必须包含大写、小写、数字和特殊字符，且不少于 8 位
      GS_PASSWORD: OpenGauss@2024
      # 初始化时只使用内置 postgres 库，业务库随后自行创建
      GS_DB: postgres
      # 库内监听端口（保持 5432，与端口映射一致）
      GS_PORT: "5432"
      # 数据库兼容模式：PG / A(Oracle) / B(MySQL)
      DBCOMPATIBILITY: PG
      # 编码
      ENCODING: UTF8
    ports:
      - "5432:5432"
    volumes:
      # 数据目录使用 Docker 命名卷，避免 Windows 绑定挂载的权限/属主问题
      - opengauss_data:/var/lib/opengauss
    shm_size: 1gb
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
      nproc:
        soft: 65536
        hard: 65536
    healthcheck:
      test:
        - CMD-SHELL
        - export PATH=/usr/local/opengauss/bin:$$PATH LD_LIBRARY_PATH=/usr/local/opengauss/lib:$$LD_LIBRARY_PATH && gsql -d postgres -U omm -h 127.0.0.1 -p 5432 -W "$${GS_PASSWORD}" -c "select 1" >/dev/null 2>&1
      interval: 10s
      timeout: 10s
      retries: 12
      start_period: 120s

volumes:
  opengauss_data:
    name: opengauss_data
```

参数逐项说明：

| 参数 | 取值 | 为什么这么配 |
| --- | --- | --- |
| `privileged: true` | 必填 | openGauss 要调整共享内存、信号量、进程数等系统级资源，官方镜像同样要求特权模式 |
| `GS_PASSWORD` | `OpenGauss@2024` | 超级用户 `omm` 的口令。**必须**同时含大写、小写、数字、特殊字符（`#?!@$%^&*-` 之一）且 ≥ 8 位，**且不能包含用户名**，否则容器拒绝初始化 |
| `GS_DB` | `postgres` | 只使用内置库，业务库按项目需要再建（避免一次性库名写死） |
| `DBCOMPATIBILITY` | `PG` | 后端 `migrate.py` 强制要求；新建业务库时也要显式带 `DBCOMPATIBILITY = 'PG'` |
| `ENCODING` | `UTF8` | 中文会话内容必需；`init_db.py` 会检查 `server_encoding` 并告警 |
| `ports` | `5432:5432` | 宿主机 5432；若被占用改成 `5433:5432` 并同步改 `.env` 的 DSN 端口 |
| 数据卷 | 命名卷 `opengauss_data` | Windows 绑定挂载会因 `chown/chmod` 失效导致启动失败，故用命名卷 |
| `shm_size` | `1gb` | openGauss 需要较大的 `/dev/shm` |
| `ulimits` | `65536` | 连接数与文件句柄，避免高并发时 `too many open files` |
| `healthcheck` | `gsql -c "select 1"` | 官方镜像里 `gsql` **不在默认 PATH**，必须显式 `export PATH` 与 `LD_LIBRARY_PATH`；`$$` 是 Compose 的转义，容器内才会展开成 `$` |
| `start_period` | `120s` | 首次初始化数据目录约 30~60 秒，期间 `health: starting` 属正常 |
| `restart` | `unless-stopped` | 随 Docker Desktop 启动自动拉起 |

> 首次启动会自动初始化数据目录（约 30~60 秒），期间 `health: starting` 属正常。
> 以 `docker inspect` 的 `State.Health.Status` 变成 `healthy` 为准，不要只看端口通。

### 3.4 启动步骤

```powershell
cd D:\工作目录\opengauss

# 1) 启动
docker compose up -d

# 2) 观察初始化（第一次约 30~60 秒）
docker compose logs -f --tail 100

# 3) 等待健康
docker compose ps
# 期望：opengauss  Up (healthy)  0.0.0.0:5432->5432/tcp
```

如果 `docker compose ps` 一直显示 `health: starting` 超过 2 分钟，先看日志关键字：

```powershell
docker compose logs --tail 200 | Select-String -Pattern "GS_PASSWORD|FATAL|failed|error" -CaseSensitive:$false
```

- 出现 `GS_PASSWORD is not meet requirements` → 口令不符合复杂度要求。
- 出现 OOM / `Cannot allocate memory` → 调小 Docker 其他容器内存，或在库内下调
  `max_process_memory` / `shared_buffers`。

### 3.5 建业务用户与业务库

本次实际用 `init\01-init-db.sql` 创建了冒烟用的 `gaussdb` / `demo`。
项目正式接入时，**建议直接建项目用的库名和用户**（与 `.env` 一致），不要沿用 `demo`：

```sql
-- 1) 业务用户（口令同样要满足复杂度）
CREATE USER app_ai WITH PASSWORD 'AppAi@Local2026';

-- 2) 业务库：必须 PG 兼容 + UTF8（CREATE DATABASE 不能放在事务块里）
CREATE DATABASE industrial_ai
  WITH OWNER = app_ai
       ENCODING = 'UTF8'
       DBCOMPATIBILITY = 'PG'
       TEMPLATE = template0;

-- 3) 授权
GRANT ALL PRIVILEGES ON DATABASE industrial_ai TO app_ai;
```

执行方式（把 SQL 拷进容器再跑，避免 Windows 侧引号转义问题）：

> 这里是本次踩得最狠的地方：**PowerShell → `docker exec` → 容器内 bash** 三层引号叠加，
> 直接拼 `bash -lc "...gsql..."` 连续失败 3 次（报 `PGDATA: not found`、`export: '-d'` 之类）。
> 最终改用"SQL 写文件 → `docker cp` → `gsql -f`"，一次通过。凡是有复杂参数或中文的
> 命令，都应走这个模式，不要试图在 PowerShell 里逐层转义。

```powershell
docker cp .\init\01-init-db.sql opengauss:/tmp/01-init-db.sql
docker exec -e LD_LIBRARY_PATH=/usr/local/opengauss/lib opengauss `
  /usr/local/opengauss/bin/gsql -d postgres -U omm -W OpenGauss@2024 -p 5432 -h 127.0.0.1 `
  -f /tmp/01-init-db.sql

# 冒烟测试（临时表，不留数据）
docker cp .\init\02-smoke-test.sql opengauss:/tmp/02-smoke-test.sql
docker exec -e LD_LIBRARY_PATH=/usr/local/opengauss/lib opengauss `
  /usr/local/opengauss/bin/gsql -d postgres -U omm -W OpenGauss@2024 -p 5432 -h 127.0.0.1 `
  -f /tmp/02-smoke-test.sql
```

> ⚠️ 仓库里的 `init\01-init-db.sql`、`02-smoke-test.sql` 在 Windows 上保存时出现过
> GBK/UTF-8 混写，中文注释在 `Get-Content` 里可能显示为乱码。部署前请用支持 UTF-8 的
> 编辑器确认编码；SQL 语句本身不受影响。

### 3.6 连接与验证

### 3.10 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 容器起不来，日志 `GS_PASSWORD is not meet requirements` | 口令缺大写/小写/数字/特殊字符，或 < 8 位 | 改 `GS_PASSWORD` 后 **`docker compose down -v`** 清卷重来（已有数据卷不会被重新初始化） |
| 健康检查一直 `starting`，但 5432 已监听 | `gsql` 不在 PATH、缺 `LD_LIBRARY_PATH`；或首次初始化未完成 | 用本文的 healthcheck（含 `export PATH`/`LD_LIBRARY_PATH`）；等满 `start_period` |
| `docker compose up` 报端口占用 | 本机已有 PostgreSQL/MySQL 等占 5432 | 改 `"5433:5432"`，同步改 DSN 端口 |
| 数据不见了 | 执行过 `docker compose down -v` | 该命令会**删除命名卷**；日常只用 `down`（保留卷） |
| Windows 绑定挂载启动失败（chown 报错） | Windows 文件系统不支持 POSIX 属主 | 用命名卷（本文做法），不要 `D:\...` 绑定挂载到 `/var/lib/opengauss` |
| 内存吃紧 / 其他容器被挤掉 | openGauss 按可见内存自动算共享内存（约 3.2GB） | 调小 Docker 其他容器，或库内下调 `max_process_memory` / `shared_buffers` |
| 后端报 `database compatibility is 'A'` | 建库时没带 `DBCOMPATIBILITY 'PG'` | 重建库（带 `DBCOMPATIBILITY = 'PG'`），再跑 `init_db.py` |
| 中文写入报错/乱码 | 库编码不是 UTF8 | `init_db.py` 的告警会提示；用 `ENCODING 'UTF8' TEMPLATE template0` 重建 |
| `docker exec ... gsql` 报找不到命令 / 缺库 | 未设置 `LD_LIBRARY_PATH`，或未用绝对路径 | 用 `/usr/local/opengauss/bin/gsql` + `-e LD_LIBRARY_PATH=/usr/local/opengauss/lib` |
| 多出意外的库名 `omm` | `GS_DB` 的默认值是 `omm`，会顺手建一个同名库 | 显式写 `GS_DB: postgres`（本文已配） |
| PowerShell 里拼 `bash -lc "...gsql..."` 连续报错（`PGDATA: not found`、`export: '-d'`） | 三层引号叠加，参数被拆错 | 改"SQL 写文件 + `docker cp` + `gsql -f`"（3.5），不要在 PowerShell 里逐层转义 |
| `applied_at` 显示 `+00` 时间 | 容器未设置 `TZ`，默认 UTC | 属正常；若要统一时区可在 compose 里加 `TZ: Asia/Shanghai`（本次未加，未验证） |
| 其他机器连不上 5432 | 容器端口已映射，但 `pg_hba.conf`/`listen_addresses` 未做远程放行（本次全程未改） | 默认只建议本机使用；确需远程访问时再配置 `pg_hba.conf` 与防火墙 |

## 4. Apache IoTDB 部署（设备时序）

### 4.1 部署形态：为什么本次是 WSL2 二进制

IoTDB 有两条路：

| 方式 | 适用 | 本次结论 |
| --- | --- | --- |
| WSL2 + 二进制（all-in-one） | 想在 Windows 上长期跑、要能改 JVM/网络参数、要 JDK 21 | **本次采用**，已跑通并保留启停脚本 |
| Docker 容器 | 与仓库 `deploy/docker-compose.yml` 统一，一条命令起 | 备选，见 4.11；容器端口/参数与本文不同 |

两条路的**连接参数一致**：`127.0.0.1:6667`、`root/root`。区别只在进程位置与配置介质。

### 4.2 前置条件

- WSL2 发行版可用（实测 `Ubuntu` 26.04 LTS，x86_64）；
- 有 JDK 21（本次装 Temurin `21.0.13` 到**用户目录**，未动系统 Java/PATH）；
- 关键约束：**WSL 内 `sudo` 需要密码**，因此全程用户级安装（不装系统包）；
- WSL 内缺 `unzip`、`jq`，用 `python3` 替代。


### 4.3 下载与校验

**版本发现**：官方指南里的正则按 `apache-iotdb-*` 匹配，与当前 Apache 发布清单
（key 为 `IoTDB-x.y.z`）不符，直接按清单解析会拿不到版本。本次手工确认最新稳定版
**2.0.11**。

**下载策略**：包从国内镜像下载，**SHA-512 只认 `downloads.apache.org` 的官方值**：

```bash
VERSION=2.0.11
BASE=$HOME/iotdb
PACKAGE=apache-iotdb-${VERSION}-all-bin.zip

# 官方校验值
curl -fsSL -o ${PACKAGE}.sha512 \
  "https://downloads.apache.org/iotdb/${VERSION}/${PACKAGE}.sha512"
EXPECTED=$(awk '{print $1; exit}' ${PACKAGE}.sha512)

# 国内镜像依次尝试
for url in \
  "https://mirrors.aliyun.com/apache/iotdb/${VERSION}/${PACKAGE}" \
  "https://mirrors.tuna.tsinghua.edu.cn/apache/iotdb/${VERSION}/${PACKAGE}" \
  "https://downloads.apache.org/iotdb/${VERSION}/${PACKAGE}" ; do
  curl -fL --retry 3 -o "${BASE}/downloads/${PACKAGE}" "$url" && \
    [ "$(sha512sum "${BASE}/downloads/${PACKAGE}" | awk '{print $1}')" = "$EXPECTED" ] && break
done
```

> ⚠️ **本次最值得复盘的坑在这里**：第一次校验失败时，脚本按"不匹配就删除"的分支写了
> `rm -f \$HOME/iotdb/downloads/apache-iotdb-2.0.11-all-bin.zip`。但脚本是通过
> **PowerShell → wsl.exe** 执行的，PowerShell 的转义符是反引号（`` ` ``），不是反斜杠，
> `\$HOME` 没有被当成字面量，`rm` 静默失效，那个 **11MB 的半包**被下一次下载
> "断点复用"（`curl -C -`）继续用了，于是校验**看起来**一直不匹配。
> 表象是"镜像文件损坏"，根因是**脚本转义错误 + 断点续传复用了坏文件**。
>
> 结论：
> 1. 跨 PowerShell 调 WSL 时，路径和 `$` 变量要格外小心，优先把脚本写成 `.sh` 文件再执行，
>    不要在 `-c "..."` / `-lc "..."` 里拼复杂命令；
> 2. 校验失败时先删干净半包再重下，并确认文件大小与官方清单一致
>    （本次完整包 `118,700,590` 字节）；
> 3. 换源后两个镜像的哈希一致（`f569…`），说明镜像本身没问题。

JDK 21 从 TUNA 的 Adoptium 镜像获取（当时 GitHub 不可达，该源**不提供官方校验值**，
只能靠 `gzip -t` + `java -version` 自检）：

```bash
JDK_TGZ=OpenJDK21U-jdk_x64_linux_hotspot_21.0.13_9.tar.gz
curl -fL --retry 5 -o "$JDK_TGZ" \
  "https://mirrors.tuna.tsinghua.edu.cn/Adoptium/21/jdk/x64/linux/${JDK_TGZ}"
tar -xzf "$JDK_TGZ" -C "$HOME/iotdb/jdk21" --strip-components=1
"$HOME/iotdb/jdk21/bin/java" -version
```

### 4.4 解压（保留权限）

WSL 内没有 `unzip`，直接用 Python 解压，并**保留 Unix 权限位**（否则 `sbin/*.sh`
不可执行）：

```python
# extract_zip.py：解压后按 zip 内记录的 Unix mode 补回权限位（关键步骤）
import os, sys, zipfile

src, dest = sys.argv[1], sys.argv[2]
os.makedirs(dest, exist_ok=True)
with zipfile.ZipFile(src) as zf:
    zf.extractall(dest)
    for info in zf.infolist():
        if info.is_dir():
            continue
        mode = (info.external_attr >> 16) & 0o7777
        if mode:
            try:
                os.chmod(os.path.join(dest, info.filename), mode)
            except OSError:
                pass
```

没有这一步时，`sbin/*.sh`、`bin/*.sh` 会丢失可执行位，启动脚本报 `Permission denied`。
仓库里保留了完整脚本 `iotdb_install/extract_zip.py`。

### 4.5 关键配置（按小内存单机调整）

配置目录：`/home/mashuai/iotdb/apache-iotdb-2.0.11-all-bin/conf/`

| 文件 | 配置项 | 值 | 目的 |
| --- | --- | --- | --- |
| `confignode-env.sh` | `MEMORY_SIZE` | `512M` | ConfigNode 堆内存（单机小内存下调） |
| `datanode-env.sh` | `MEMORY_SIZE` | `1G` | DataNode 堆内存 |
| `iotdb-system.properties` | `dn_rpc_address` | `0.0.0.0` | WSL2 的 localhost 转发只转发绑定在 `0.0.0.0` 的服务；绑 127.0.0.1 时 Windows 访问不到 |
| `datanode-env.sh` | `IOTDB_JVM_OPTS` 追加 | `-Djava.net.preferIPv4Stack=true` | 不加时 JVM 绑到 IPv6 通配，WSL 只暴露 `[::1]`，Windows 的 `127.0.0.1:6667` 不通 |
| shell | `ulimit -n` | `65535` | 避免文件句柄不足 |

追加 JVM 参数的方式（保持幂等，只在缺失时追加）：

```bash

# Added by installer: force IPv4 so WSL2 localhostForwarding exposes 127.0.0.1:6667
IOTDB_JVM_OPTS="${IOTDB_JVM_OPTS:-} -Djava.net.preferIPv4Stack=true"
EOF
```

### 4.6 启动顺序（ConfigNode → DataNode）

**必须按顺序起**：先 ConfigNode（10710 RPC），端口就绪后再起 DataNode（6667 SQL）。
并且要用 `setsid nohup ... &` 脱离当前 shell，否则 `wsl.exe` 命令一退出，JVM 就被带停。

```bash
cd "$IOTDB_HOME"

# 1) ConfigNode
setsid nohup bash sbin/start-confignode.sh > logs/console-confignode.out 2>&1 < /dev/null &
# 等待 10710 监听，最多 120s
for i in $(seq 1 60); do ss -ltn | grep -q ':10710\b' && break; sleep 2; done
sleep 3

# 2) DataNode：失败要重试（ConfigNode 刚起时 DataNode 会 Connection refused）
dn_started=0
for attempt in 1 2; do
  setsid nohup bash sbin/start-datanode.sh > logs/console-datanode.out 2>&1 < /dev/null &
  ok=0
  for i in $(seq 1 45); do        # 等待 6667 监听，最多 90s
    ss -ltn | grep -q ':6667\b' && { ok=1; break; }
    sleep 2
  done
  [ "$ok" = 1 ] && { dn_started=1; break; }
  pkill -f 'org\.apache\.iotdb\.db\.service\.DataNode' || true
done
[ "$dn_started" = 1 ] || { echo "DataNode 启动失败，看 logs/log_datanode_all.log" >&2; exit 1; }
```

> 本次踩坑：DataNode 用**前台**方式启动（`bash sbin/start-datanode.sh` 不加后台）时反复失败；
> 改成 `setsid nohup ... &` 后台启动 + 等 ConfigNode 端口就绪后再起，稳定成功。
> 失败时看 `logs/log_datanode_all.log` 与 `logs/console-datanode.out`，不要只看进程列表。

### 4.12 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| DataNode 反复退出，6667 不通 | 前台方式启动被杀；或 ConfigNode 未就绪就起 DataNode（日志常见 `Connection refused` / `Cannot pull system configurations`） | 用 `setsid nohup ... &`，等 10710 后再起 DataNode，失败重试并看 `log_datanode_all.log` |
| WSL 内 `ss -ltn` 有 6667，Windows 连不上 | 绑在 `127.0.0.1`（未暴露给 WSL 转发）或绑在 IPv6 通配 | `dn_rpc_address=0.0.0.0` + `-Djava.net.preferIPv4Stack=true` |
| `cli.sh` 报 `IoTDB is not installed` | `IOTDB_HOME` / `JAVA_HOME` 未设置 | 用封装脚本（内部已 export），确认 `~/iotdb/apache-iotdb-2.0.11-all-bin` 存在 |
| 下载后 SHA-512 不匹配 | 镜像文件截断/损坏 | 换另一个镜像重下；校验值只认 `downloads.apache.org` |
| 解压后 `sbin/*.sh` 不可执行 | 用不保权限的工具解压 | 用项目内 `extract_zip.py`，或 `chmod +x sbin/*.sh bin/*.sh` |
| `show databases` 结果"少库" | 表模型与树模型方言不同 | 明确当前方言；后端用树模型，安装冒烟用表模型 |
| 内存不足 / WSL 卡 | 默认堆内存偏大 | 调 `MEMORY_SIZE`（512M / 1G），改完 `stop` 再 `start` |
| Windows 重启后连不上 | WSL 停止，IoTDB 未自启 | 手工 `start-iotdb.cmd`，或配置「登录时」任务计划 |

## 5. Milvus 部署（RAG 向量库）

### 5.1 组件与端口

Milvus standalone 由三个容器组成，顺序依赖固定：

```text
milvus-volume-init   一次性容器：修正 /var/lib/milvus 属主（v3 权限要求），成功后退出
```

| `9000` | MinIO S3 API | 本机可不暴露 |
| `9001` | MinIO 控制台 | 本机可不暴露 |
| `2379` | etcd | **不要**暴露 |

关键点：

- 数据卷路径由 `${DOCKER_VOLUME_DIRECTORY:-.}` 决定：不设该环境变量时，默认落在
  **当前目录**下的 `.\volumes\`（即 `C:\milvus\volumes\`）。所以必须在 `C:\milvus`
  目录里执行 `docker compose`，否则数据会跑到别的目录。
- `milvus-volume-init` 是 **v3 专属的一次性权限修正容器**：以 root 把 `/var/lib/milvus`
  `chown` 给 `milvus` 用户，成功后写 `.milvus-volume-owner-<uid>-<gid>` 标记并退出。
  它必须 `condition: service_completed_successfully`，否则 standalone 会因权限失败。
- 从别处恢复数据后，若属主变了，要**删掉该标记文件**让修正逻辑重跑。
- `standalone` 依赖 etcd/minio 只是 `service_started`（不是 healthy），所以首次可能还要等
  几十秒才真正可查询；以 `9091/healthz` 返回 `OK` 为准。
- `seccomp:unconfined` 是 Milvus 官方要求，不要删。

### 5.5 端到端自检（不装 SDK，直接 REST）

```powershell
$ProgressPreference = 'SilentlyContinue'
$base = 'http://127.0.0.1:19530/v2/vectordb'
function Post($p, $b) {
  Invoke-RestMethod -Method Post -Uri "$base/$p" -ContentType 'application/json' `
    -Body ($b | ConvertTo-Json -Depth 10 -Compress) -TimeoutSec 30
}

$vec = @(0.11,0.22,0.33,0.44,0.55,0.66,0.77,0.88)

# 1) 建集合（quick create，自动带 AUTOINDEX 索引）
Post 'collections/create' @{ collectionName='demo_e2e'; dimension=8; metricType='COSINE';
  primaryFieldName='id'; vectorFieldName='vector'; idType='Int64'; autoID=$false }

# 2) 插 3 条
Post 'entities/insert' @{ collectionName='demo_e2e'; data=@(
  @{ id=1; vector=$vec },
  @{ id=2; vector=@(0.88,0.77,0.66,0.55,0.44,0.33,0.22,0.11) },
  @{ id=3; vector=@(0.5,0.5,0.5,0.5,0.5,0.5,0.5,0.5) } ) }

# 3) load 后检索
Post 'collections/load' @{ collectionName='demo_e2e' }
Start-Sleep -Seconds 3
Post 'entities/search' @{ collectionName='demo_e2e'; data=@(,$vec); annsField='vector';
  limit=3; outputFields=@('id') }

# 4) 清理
Post 'collections/drop' @{ collectionName='demo_e2e' }
```

实测检索返回 TopK 相似度 `0.9999 / 0.8911 / 0.5882`，符合余弦相似度预期。

> 踩坑：quick create 的集合**已经自动建了索引**，再调 `indexes/create` 会报
> `code 1100: creating multiple indexes on same field`；需要自定义索引时，先建 schema/集合
> 再建索引，或直接接受 AUTOINDEX。另：`get_stats` 的 `rowCount` 在未 flush 前可能为 0，
> 属正常（数据还在 growing segment），不是丢数据。

| 会话不落库 | `OPENGAUSS_DSN` 为空 | 配 DSN 后重启后端 |
| 时序查询为空 | 只建了表模型库，后端要树模型 `root.mes` | 跑 `init_db.py --only iotdb` |
| 知识检索报集合不存在 | 未跑 `build_knowledge.py`，或 `KB_NAME` 不符 | 构建知识库，核对集合名 `<KB_NAME>__<version>` |
| 插入向量维度不符 | `EMBEDDING_DIMENSIONS` 与实际模型不一致 | 统一维度后重建集合 |
| `/health` 中某项 down | 对应服务未起或端口错 | 按 6.4 逐项排查 |

### 7.1 启停命令速查

| 服务 | 启动 | 停止 | 状态 |

### 7.2 备份策略

| 对象 | 方式 | 建议频率 | 恢复 |
| --- | --- | --- | --- |
| openGauss | `gs_dump` 逻辑备份（3.8） | 每日 / 变更前 | `gsql -f` 导入空库 |
| openGauss | 命名卷目录快照 | 每周 | 停容器后替换卷 |
| IoTDB | 停服后打包 `.../data` 目录 | 每周 | 停服后还原目录 |
| Milvus | 停服打包 `volumes\` 全体 | 每周 / 重建知识库前 | 还原目录 + 删属主标记 |
| 三库配置 | `docker-compose.yml`、`.env`、脚本 | 随变更 | 版本库/共享盘 |

### 7.3 升级

1. 先备份（7.2），并记下当前镜像 tag / digest；
2. 改 compose 中的 `image` tag（openGauss/Milvus）或重新下载解压（IoTDB），
   **不要跨大版本直接覆盖数据目录**；
3. `docker compose up -d` 拉起，观察健康状态；
4. 跑 6.4 全量检查与 `scripts/check.py`；
5. 回滚：改回旧 tag + 还原备份。Milvus 跨大版本升级前务必看官方 release notes，
   必要时用官方迁移工具而不是直接换镜像。

### 7.4 危险操作清单

| 操作 | 后果 | 建议 |
| --- | --- | --- |
| `docker compose down -v` | 删除 openGauss/Milvus 数据卷 | 只在确认可重建时执行 |
| 改 `GS_PASSWORD` 后重建 | 仅对新初始化生效；老实例数据仍在但密码不变 | 用 `ALTER USER` 改密码（3.9） |
| `rm -rf ~/iotdb` | 删除 IoTDB 全部数据 | 先停服并备份 `data` |
| 删除 `volumes\milvus` | 向量与元数据全丢 | 先停服、备份 |
| 直接改 `volumes` 属主 | 可能导致 Milvus 启动失败 | 交给 `milvus-volume-init` |

## 8. 生产化差异（ARM64 算力服）

本文参数是**本机 x86_64 开发环境**的实测值。迁移到 B 算力服（鲲鹏 920 / 昇腾 300I A2 /
银河麒麟 ARM64）时，以下项目必须重新评估，**不能直接照搬**：

### 8.1 必须替换的项

| 项 | 本机（本文） | 生产要求 |
| --- | --- | --- |
| 镜像架构 | `enmotech/opengauss:6.0.0` 实测为 x86_64 | 必须改用 **aarch64** 镜像或官方 ARM64 tag，并用 `docker image inspect` 核对 `Architecture` |
| 密码 | `OpenGauss@2024`、`root/root`、`minioadmin` | 全部替换为强口令，进密码管理系统；openGauss 用 `ALTER USER` 改 |
| 端口绑定 | `0.0.0.0:5432` 等对全网卡 | 改为 `127.0.0.1:5432:5432` 等，仅回环或独立 Docker 网络 |
| Milvus 依赖 | 独立 etcd + MinIO 容器，暴露 9000/9001 | 关闭 9000/9001 对外映射；MinIO 使用强凭据 |
| 数据位置 | 命名卷 / `C:\milvus\volumes` | 生产用宿主机磁盘 + 定期备份；注意 openGauss 数据量增长 |
| 版本固定 | tag（`6.0.0`、`v3.0.5`） | 固定到 **digest**，避免 tag 漂移；离线环境用镜像 tar 导入 |
| 开机自启 | Docker Desktop + `restart: unless-stopped` | systemd 管理（或 `docker.service` + `restart`），IoTDB 不进 WSL |

### 8.2 架构核查命令

```bash
# 在 B 机上确认宿主架构
uname -m            # 期望 aarch64
docker image inspect <image> --format '{{.Architecture}} {{.Os}}'   # 期望 arm64 linux
docker manifest inspect <image> | grep -i architecture
```

IoTDB 若在生产用二进制方式：Linux ARM64 需 `aarch64` 版 JDK 与对应架构的
`all-bin` 包（Apache 发布有 aarch64 包，需确认版本）；若用容器，`apache/iotdb` 官方镜像
为多架构，需核对 manifest。

### 8.3 与仓库生产指南的衔接

- 端口、Nginx、systemd、证书等上层部署见 [代码部署指南](./代码部署指南.md) 第 5 章；
- 该文档 5.4 节已明确：仓库 `deploy/docker-compose.yml` **只适合本地开发**，
  生产至少要做"改密码、绑回环、MQTT 认证、持久化卷、固定镜像、ARM64 镜像"六项调整；
- 本文第 3~5 章的初始化、验证、备份步骤在生产同样适用，只是参数与路径不同。

### 8.4 待确认项（本次未验证）

以下内容没有在 ARM64 生产环境实测，交付前需现场确认：
