## 1. 部署结论与总体设计

### 1.1 结论先行

- 三个库**全部容器化**，用一份 compose 编排，镜像固定到 **digest**，在 ARM64 上运行。
- 所有数据库端口**只绑定 `127.0.0.1`**，不对外网、不对用户网段开放；后端与库同机。
- 数据落在 Docker 数据根目录 `/data/docker`（环境手册已把 `data-root` 指向 4 TB 盘），
  用**明确命名的 volume**，便于备份和迁移。
- 备份统一落在 `/data/mes/backup`，配置与密钥在 `/opt/mes/db`、`/etc/mes`。
- 版本采用仓库生产编排中的版本，不沿用开发机的版本（见 1.3 差异表）。

### 1.2 版本与端点（生产基线）

| 组件 | 镜像（含 arm64 manifest） | 容器名 | 宿主端口（仅回环） | 用途 |
| --- | --- | --- | --- | --- |
| openGauss | `opengauss/opengauss-server:7.0.0-RC3.B025` | `industrial-ai-opengauss` | `127.0.0.1:15432` → 容器 5432 | 会话、工单副本、报告记录 |
| Apache IoTDB | `apache/iotdb:2.0.11-standalone` | `industrial-ai-iotdb` | `127.0.0.1:6667` | 设备时序、MQTT 水位线 |
| Milvus | `milvusdb/milvus:v2.6.26`（standalone，内嵌 etcd + 本地存储） | `industrial-ai-milvus` | `127.0.0.1:19530`、`127.0.0.1:9091` | 知识库向量与检索 |

配套事实：

- openGauss 的**默认超级用户是 `gaussdb`**（官方镜像），不是开发机 enmotech 镜像的 `omm`。
- IoTDB standalone 单容器内是 `1 ConfigNode + 1 DataNode`，对外只有 6667。
- Milvus v2.6.26 用 `ETCD_USE_EMBED=true` + `COMMON_STORAGETYPE=local`，
  **不需要单独部署 etcd 和 MinIO**，离线制品只有 1 个镜像。

### 1.3 与开发机环境的差异（照抄会踩的坑）

| 项 | 开发机（本机文档） | 生产（本文） | 照抄后果 |
| --- | --- | --- | --- |
| openGauss 端口 | 5432 | **15432** | 后端 DSN 端口错，连不上 |
| openGauss 管理员 | `omm`（enmotech 镜像） | **`gaussdb`**（官方镜像） | `init_db.py --admin-dsn` 认证失败 |
| openGauss 数据库 | `demo`（验证库） | **`industrial_ai`**（项目库） | 后端连到空库 |
| Milvus 版本 | v3.0.5 | **v2.6.26** | 数据卷不兼容，不能互换 |
| IoTDB 形态 | WSL2 二进制 | **容器**（如需二进制见 7.8） | 无 systemd、开机不自启 |
| 密码 | `OpenGauss@2024` 等弱口令 | 随机强口令，存 `/opt/mes/db/.env` 与 `/etc/mes/compute-service.env` | 安全审计不通过 |

### 1.4 部署拓扑

```text
B 算力服（aarch64 / 麒麟 / 192.168.50.20）
├─ FastAPI 127.0.0.1:8000        （systemd，见代码部署指南）
├─ Nginx   0.0.0.0:8443          （仅 A 访问）
└─ Docker（data-root=/data/docker）
   ├─ industrial-ai-opengauss   127.0.0.1:15432 → 5432
   ├─ industrial-ai-iotdb       127.0.0.1:6667
   └─ industrial-ai-milvus      127.0.0.1:19530 / 9091
```

所有库只在本机回环可达，A 和 Windows 端都接触不到数据库。

### 1.5 上线顺序（首次部署按此执行）

```text
0. 系统基线        → 环境配置手册（时区、chrony、sysctl、limits、Docker、/data/docker）
1. 部署前检查      → 本文第 2 章
2. 导入离线镜像    → 本文第 3 章
3. 目录与密钥      → 本文第 4 章
4. 起三库          → 本文第 6/7/8 章
5. 初始化数据库    → 本文第 9.2 节（init_db.py、build_knowledge.py）
6. 配后端 .env     → 本文第 9.1 节 + 代码部署指南 5.5/5.7

```

## 2. 部署前检查

> 全部命令在 B 的 root shell 执行。`sudo` 可加可不加，结果一致。

### 2.1 架构与系统

```bash
uname -m                      # 期望 aarch64（若为 x86_64，本文镜像与结论全部不适用）
cat /etc/os-release           # 期望麒麟 Kylin V10 系列
uname -r
getconf LONG_BIT              # 期望 64
```

### 2.2 基础系统参数（来自环境配置手册，需确认已生效）

```bash
timedatectl                         # Time zone: Asia/Shanghai，System clock synchronized: yes
systemctl is-active chronyd          # active
sysctl vm.max_map_count vm.swappiness fs.file-max
# 期望 262144 / 1 / 1048576
ulimit -n                           # 期望 1048576（登出重登后生效）
free -g                             # 确认总内存与可用内存
df -h /data                         # 确认 4TB 盘已挂载
```

`vm.max_map_count=262144` 对 Milvus 尤其重要；`ulimit -n` 影响三库的并发连接。

### 2.3 Docker 与 Compose

```bash
docker --version
docker compose version
docker info --format 'Architecture={{.Architecture}} CgroupDriver={{.CgroupDriver}} Root={{.DockerRootDir}}'
# 期望 Architecture=aarch64（部分版本显示 arm64）、CgroupDriver=systemd、Root=/data/docker
systemctl is-active docker           # active
docker buildx version                # 需要 buildx 来核对 manifest/digest
```

`CgroupDriver` 必须是 `systemd`（环境手册的 daemon.json 已配置），否则容器 cgroup 可能异常。
`DockerRootDir` 必须是 `/data/docker`，否则数据会写满系统盘。

### 2.4 端口占用基线

```bash
for p in 15432 6667 19530 9091; do
  ss -lntp | grep -q ":$p " && echo "OCCUPIED $p" || echo "free $p"
done
```

若被占用，先定位进程（`ss -lntp | grep :15432`），不要直接改端口——端口一改，
第 9 章 `.env` 与验收命令都要同步改。

### 2.5 防火墙与 SELinux

```bash
firewall-cmd --state
firewall-cmd --list-ports
firewall-cmd --list-rich-rules
getenforce
```

要求：

- 防火墙**不开放** `15432 / 6667 / 19530 / 9091`（只允许 A 访问 8443，见代码部署指南 5.9）；
- SELinux 若为 `Enforcing`，Docker 的 bind mount 需要 `:z` 标签；本文配置挂载点在
  `/opt/mes/db/milvus/*.yaml`，首次启动若报 `Permission denied`，按 12.2 处理。

> ⚠️ **Docker 会绕过 firewalld**：`docker run -p` 发布的端口会写入 `DOCKER` iptables 链，
> firewalld 的 `--remove-port` 不生效。所以"只绑回环"（`127.0.0.1:15432:5432`）不是可选项，
> 而是生产安全边界；靠防火墙挡数据库端口是挡不住的。

### 2.6 离线条件确认

```bash
timeout 5 curl -sI https://registry-1.docker.io/v2/ >/dev/null && echo "外网可达" || echo "外网不可达（按第 3 章离线导入）"
timeout 5 curl -sI https://pypi.org/simple/ >/dev/null && echo "PyPI 可达" || echo "PyPI 不可达（需本地 wheelhouse）"
```

多数现场是"外网不可达"。只要不可达，就必须走第 3 章的镜像导出/导入，不能指望
`docker compose up` 自行拉取。

## 3. 离线制品准备

> 现场若不能直连外网，制品必须在**外网机**（与本机同为 arm64，或在 amd64 机上
> 用 `--platform linux/arm64` 拉取）准备，再经内网中转机导入。
> 这与环境配置手册第 10 章的 EXT-IMG 流程一致。

### 3.1 需要准备的制品清单

| 制品 | 文件示例 | 来源 |
| --- | --- | --- |
| openGauss 镜像 | `opengauss-server-7.0.0-RC3.B025-arm64.tar` | `opengauss/opengauss-server` |
| IoTDB 镜像 | `iotdb-2.0.11-standalone-arm64.tar` | `apache/iotdb` |
| Milvus 镜像 | `milvus-v2.6.26-arm64.tar` | `milvusdb/milvus` |
| 配置文件 | `db-configs.tar.gz`（compose + milvus 配置） | 本文第 6/8 章 |
| 校验清单 | `SHA256SUMS` | 见 3.4 |

**不需要** etcd/MinIO 镜像：Milvus 用内嵌 etcd + 本地存储（1.2）。
若现场决定改用外置 etcd/MinIO，再按 8.9 追加。

### 3.2 在外网机导出

```bash
# 逐架构拉取，确保产物只有 arm64
docker pull --platform linux/arm64 opengauss/opengauss-server:7.0.0-RC3.B025
docker pull --platform linux/arm64 apache/iotdb:2.0.11-standalone
docker pull --platform linux/arm64 milvusdb/milvus:v2.6.26

docker save -o opengauss-server-7.0.0-RC3.B025-arm64.tar \
  opengauss/opengauss-server:7.0.0-RC3.B025
docker save -o iotdb-2.0.11-standalone-arm64.tar \
  apache/iotdb:2.0.11-standalone
docker save -o milvus-v2.6.26-arm64.tar \
  milvusdb/milvus:v2.6.26
```

Windows 外网机等价命令：

```powershell
docker pull --platform linux/arm64 opengauss/opengauss-server:7.0.0-RC3.B025
docker save -o "D:\offline\images\opengauss-server-7.0.0-RC3.B025-arm64.tar" `
  opengauss/opengauss-server:7.0.0-RC3.B025
Get-FileHash "D:\offline\images\opengauss-server-7.0.0-RC3.B025-arm64.tar" -Algorithm SHA256
```

**导出后必须确认真的是 arm64**：

```bash
docker image inspect opengauss/opengauss-server:7.0.0-RC3.B025 \
  --format '{{.Architecture}}'
# 期望 arm64；若是 amd64，说明 --platform 没生效，重导
```

> 外网机若是国内网络、Docker Hub 直连超时，可用国内镜像站拉取后**重打成官方名**再 save，
> 这样 compose 不用改镜像地址：
>
> ```bash
> docker pull --platform linux/arm64 docker.m.daocloud.io/opengauss/opengauss-server:7.0.0-RC3.B025
> docker tag  docker.m.daocloud.io/opengauss/opengauss-server:7.0.0-RC3.B025 \
>             opengauss/opengauss-server:7.0.0-RC3.B025
> ```
>
> 本次的 manifest digest 就是这样核实的（镜像站是代理，内容寻址的 digest 与官方一致）。

### 3.3 在内网机导入

```bash
mkdir -p /data/pkg/images
# scp *.tar root@192.168.50.20:/data/pkg/images/

cd /data/pkg/images
sha256sum -c SHA256SUMS           # 先校验传输完整性

for f in *.tar; do
  echo "== load $f"
  docker load -i "$f" || exit 1
done

for img in \
  opengauss/opengauss-server:7.0.0-RC3.B025 \
  apache/iotdb:2.0.11-standalone \
  milvusdb/milvus:v2.6.26 ; do
  printf '%-55s %s\n' "$img" \
    "$(docker image inspect "$img" --format '{{.Architecture}}')"
done
# 三行都必须是 arm64
```

### 3.4 校验清单与固定 digest

在外网机核对 digest：

```bash
for img in \
  opengauss/opengauss-server:7.0.0-RC3.B025 \
  apache/iotdb:2.0.11-standalone \
  milvusdb/milvus:v2.6.26 ; do
  echo "== $img"
  docker buildx imagetools inspect "$img" | head -6
done
```

本次核实到的 manifest digest（多架构 index，含 amd64/arm64）：

| 镜像 | manifest digest |
| --- | --- |
| `opengauss/opengauss-server:7.0.0-RC3.B025` | `sha256:d554be1b8b08165a8b19348f0ca236b5d61a4832ffadac0340ded973c34f38e4` |
| `apache/iotdb:2.0.11-standalone` | `sha256:5ace0f3eceff892dd349d02288224c966f3fdeb11d08c4f575b642a110b82338` |
| `milvusdb/milvus:v2.6.26` | `sha256:f43e0cd0c9912c35379c349f7f3a3a806b9308462d43d1bfa18d007c6642d693` |

> 这些 digest 通过镜像站解析得到，与官方 registry 应一致（内容寻址）。
> 交付时仍以现场 `docker buildx imagetools inspect` 输出为准；不一致时以现场为准并记录。

固定 digest 的写法：

```yaml
image: opengauss/opengauss-server:7.0.0-RC3.B025@sha256:d554be1b8b08165a8b19348f0ca236b5d61a4832ffadac0340ded973c34f38e4
```

## 4. 目录、数据盘与密钥

### 4.1 目录规划

```bash
mkdir -p \
  /opt/mes/db \
  /opt/mes/db/milvus \
  /data/pkg/images \
  /data/mes/backup \
  /etc/mes

chown -R root:root /opt/mes/db /etc/mes
chmod 700 /etc/mes
```

| 路径 | 内容 | 权限 |
| --- | --- | --- |
| `/opt/mes/db/docker-compose.yml` | 三库编排 | `root:root 0644` |
| `/opt/mes/db/.env` | compose 插值变量（管理密码） | **`root:root 0600`** |
| `/opt/mes/db/milvus/embedEtcd.yaml`、`user.yaml` | Milvus 配置 | `root:root 0644` |
| `/etc/mes/compute-service.env` | 后端环境变量（含三库 DSN） | **`root:root 0600`** |
| `/data/mes/backup` | 备份输出 | `root:root 0700` |
| `/data/pkg/images` | 离线镜像 tar | `root:root 0644` |
| `/data/docker/volumes/mes-*` | 实际数据（volume） | 由 Docker 管理 |

### 4.2 数据卷命名（显式，便于备份）

compose 中给每个 volume 显式 `name:`，避免项目名前缀带来的歧义：

| volume | 实际落盘 | 内容 |
| --- | --- | --- |
| `mes-opengauss-data` | `/data/docker/volumes/mes-opengauss-data/_data` | openGauss 数据目录 |
| `mes-iotdb-data` | `/data/docker/volumes/mes-iotdb-data/_data` | IoTDB 数据 |
| `mes-iotdb-logs` | `/data/docker/volumes/mes-iotdb-logs/_data` | IoTDB 日志 |
| `mes-milvus-data` | `/data/docker/volumes/mes-milvus-data/_data` | Milvus 元数据 + 本地存储 |

用 `docker volume inspect mes-opengauss-data --format '{{.Mountpoint}}'` 核对。

### 4.3 密钥与 `.env`

**不要**把密码写进 compose、Markdown、Git 或聊天记录。用随机口令：

```bash
# 前缀保证含大写/小写/数字/特殊字符，再接 20 位随机串；
# 若用户名是 gaussdb，务必确认生成结果里不含 "gaussdb"（概率极低，但要检查）
PW="Aa1!$(openssl rand -base64 18 | tr -d '/+=' | cut -c1-20)"
echo "$PW"
```

openGauss 口令有**硬性复杂度要求**（不满足直接初始化失败）：

- 长度 ≥ 8；
- 至少包含大写、小写、数字、特殊字符（`#?!@$%^&*-` 之一）；
- **不能包含用户名**（例如用户 `gaussdb` 时，口令里不能出现 `gaussdb`）。

写入 `/opt/mes/db/.env`（仅 compose 用）：

```ini
# /opt/mes/db/.env  —— chmod 600 root:root
OPENGAUSS_ADMIN_PASSWORD=<替换为符合复杂度的强口令>
```

`compose` 通过变量插值读取；**不要**在 compose 里直接写明文。

后端密钥写入 `/etc/mes/compute-service.env`（见 9.1），由 systemd `EnvironmentFile` 注入。

### 4.4 密钥登记

口令保管人、生成时间、轮换周期（建议 90 天）、备份加密口令都要登记。
**文档里只出现占位符 `<...>`。**

## 5. 安全基线

### 5.1 三个库的暴露面

| 库 | 必须满足 | 禁止 |
| --- | --- | --- |
| openGauss | 只监听 `127.0.0.1:15432` | 对 A 网段或用户网段开放 15432 |
| IoTDB | 只监听 `127.0.0.1:6667` | 开放 10710/10730 等内部端口 |
| Milvus | 只监听 `127.0.0.1:19530/9091` | 开放 9091 给用户网段 |

验证"外部真的进不来"：

```bash
# 在 A 或用户电脑上执行，应全部失败
nc -zv 192.168.50.20 15432
nc -zv 192.168.50.20 6667
nc -zv 192.168.50.20 19530
nc -zv 192.168.50.20 9091

# B 本机确认监听地址
ss -lntp | grep -E ':(15432|6667|19530|9091)\b'
# 期望全是 127.0.0.1:xxxx，不能出现 0.0.0.0 或 [::]
```

`ss` 中出现 `0.0.0.0` 或 `[::]` 就是配置错了，回 6/7/8 章改 `ports` 绑定。

### 5.2 认证

| 组件 | 默认 | 生产动作 |
| --- | --- | --- |
| openGauss | `gaussdb` + `.env` 中强口令 | 保持；业务用户 `app_ai` 独立口令 |
| IoTDB | `root/root` | **必须改**（7.4） |
| Milvus | 默认免认证 | 建议开启认证，见 8.6 |
| MinIO/etcd | 内嵌，不出容器 | 无需单独处理 |

### 5.3 密钥文件权限复核


## 6. openGauss 生产部署

### 6.1 镜像与关键事实

| 项 | 值 |
| --- | --- |
| 镜像 | `opengauss/opengauss-server:7.0.0-RC3.B025` |
| 架构 | manifest 含 `arm64`（本次已核实） |
| 默认超级用户 | **`gaussdb`** |
| 库内端口 | 5432；宿主映射 **15432** |
| 兼容模式 | `DBCOMPATIBILITY = PG`（后端强制校验） |
| 数据卷 | `mes-opengauss-data:/var/lib/opengauss` |

> 7.0.0-RC3 是候选发布版。若项目验收要求稳定版，需先确认有对应 tag 的 ARM64 镜像，
> 再整体替换本文的 tag/digest；**不要**在没有对应 arm64 manifest 的版本上强推。

### 6.2 编排文件（openGauss 段）

`/opt/mes/db/docker-compose.yml`（三库合一；MQTT 不在此文件，见 9.6）：

```yaml
name: industrial-ai

services:
  opengauss:
    image: opengauss/opengauss-server:7.0.0-RC3.B025
    # 需要固定版本时改为：
    # opengauss/opengauss-server:7.0.0-RC3.B025@sha256:d554be1b...
    container_name: industrial-ai-opengauss
    hostname: opengauss
    privileged: true                    # openGauss 需要调整共享内存/信号量/进程数
    restart: unless-stopped
    environment:
      GS_PASSWORD: ${OPENGAUSS_ADMIN_PASSWORD:?set OPENGAUSS_ADMIN_PASSWORD in .env}
      # 只设置管理员口令，其余走镜像默认（与仓库 backend/deploy/docker-compose.yml 一致）。
      # 业务库的兼容模式/编码由 init_db.py 的 CREATE DATABASE 显式指定，不依赖镜像 env。
    ports:
      - "127.0.0.1:15432:5432"          # 只回环，禁止 0.0.0.0
    volumes:
      - mes-opengauss-data:/var/lib/opengauss
    shm_size: 8gb
    ulimits:
      nofile:
        soft: 1048576
        hard: 1048576
      nproc:
        soft: 65536
        hard: 65536
    healthcheck:
      test: ["CMD-SHELL", "bash -c 'echo > /dev/tcp/127.0.0.1/5432'"]
      interval: 15s
      timeout: 5s
      retries: 40
      start_period: 180s
```

> 这是 `docker-compose.yml` 的 `services.opengauss` 段；顶层的 `volumes:` 声明与三库完整
> 文件见 **14.6**，不要分别复制各章的片段拼成多个 `volumes:` 顶层键（YAML 会重复键报错）。

关键点：

- `shm_size: 8gb`：生产数据量与连接数都比开发机大，1 GB 不够时会出现共享内存报错；
  若整机内存紧张可下调，但要同步观察 6.6 的参数。
- `healthcheck` 用 TCP 探活而不依赖 `gsql` 路径：官方镜像里 `gsql` 的实际路径
  可能与本机 enmotech 镜像不同，TCP 探活不挑版本；版本/兼容性用 6.5 的命令单独验证。
- `privileged: true` 不能省；业务库的 `DBCOMPATIBILITY 'PG'` / `ENCODING 'UTF8'`
  在 6.4 建库时显式指定，这是后端能否启动的硬条件。

### 6.4 初始化项目库

生产**不要**沿用 `demo` 库。两种方式，选一种。

**方式 A（推荐）：用后端脚本自动建用户/库/schema**

```bash
cd /opt/mes/backend/current
ADMIN_PW=$(grep -E '^OPENGAUSS_ADMIN_PASSWORD=' /opt/mes/db/.env | cut -d= -f2-)

  --admin-dsn "host=127.0.0.1 port=15432 dbname=postgres user=gaussdb password=${ADMIN_PW}"
```

脚本会：建 `app_ai` 用户（口令取自 `OPENGAUSS_DSN`）→ 建 `industrial_ai`
（`DBCOMPATIBILITY 'PG'`、`ENCODING 'UTF8'`）→ 建同名 schema → 执行迁移。

**方式 B：手工执行 SQL**

```sql
CREATE USER app_ai WITH PASSWORD '<APP_AI_PASSWORD>';
CREATE DATABASE industrial_ai
  WITH OWNER = app_ai
       ENCODING = 'UTF8'
       DBCOMPATIBILITY = 'PG'
       TEMPLATE = template0;
GRANT ALL PRIVILEGES ON DATABASE industrial_ai TO app_ai;
```

> `CREATE DATABASE` 不能放在事务块里；一次只执行一条。

### 6.5 连接与版本验证

先用 `docker exec` 找到镜像里的 `gsql` 路径：

```bash

```

之后统一用这个路径：

```bash
GSQL=/usr/local/opengauss/bin/gsql     # 按上一步输出替换

docker exec -e LD_LIBRARY_PATH=/usr/local/opengauss/lib industrial-ai-opengauss \
  "$GSQL" -d postgres -U gaussdb -W "$ADMIN_PW" -p 5432 -h 127.0.0.1 \
  -c "select version();" \
  -c "select datname, datcompatibility, pg_encoding_to_char(encoding) from pg_database order by 1;"
```

验收标准：

- `version()` 显示 openGauss 7.0.0；
- `industrial_ai` 的 `datcompatibility = PG`、编码 `UTF8`；
- 业务用户能连上：

### 6.6 内存与容量（与 vLLM 共存）

128 GB 是整机预算，vLLM 要占大头。openGauss 会按**可见内存**自动估算共享内存，
在 128 GB 机器上可能一次占走几十 GB，把 vLLM 挤到 OOM。**首次启动后必须实测并限制**：

```bash
# 1) 看容器实际占用
docker stats --no-stream industrial-ai-opengauss

# 2) 看库内关键参数
docker exec -e LD_LIBRARY_PATH=/usr/local/opengauss/lib industrial-ai-opengauss \
  "$GSQL" -d postgres -U gaussdb -W "$ADMIN_PW" -p 5432 -h 127.0.0.1 \
  -c "show shared_buffers;" -c "show max_process_memory;"
```

若超出预算（建议 openGauss 控制在 **8~12 GB**），进库调整后重启容器：

```sql
ALTER SYSTEM SET max_process_memory = '8GB';
ALTER SYSTEM SET shared_buffers = '2GB';
```

```bash
docker restart industrial-ai-opengauss
```

> `ALTER SYSTEM` 持久化，重启后仍生效。8 GB / 2 GB 是"128 GB 整机、vLLM 共存"场景下的
> **起点值**，需按目标机实测确定；调整后回归 6.5 与后端 `check.py`。

磁盘：会话数据量小，`du -sh /data/docker/volumes/mes-opengauss-data` 日常几 GB 量级；
按 11.5 的留存策略控制。

### 6.7 备份与恢复

### 6.8 升级与回滚

1. 先备份（6.7）；
2. 改 compose 的 tag/digest，或导入新镜像；
3. `docker compose up -d opengauss`，观察 healthy；
4. 跑 6.5 验证 + 后端 `check.py`；
5. 回滚：改回旧 digest + `up -d`；**若迁移已执行且不可逆，必须同时还原备份**。

> 迁移脚本只向前执行（`app_migrations` 记录版本）。升级前不备份 = 无法回滚。

### 6.9 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `GS_PASSWORD is not meet requirements` | 口令不满足 4.3，或包含用户名 | 改口令后 `docker compose down -v` 重建 |
| 容器起不来，日志提示共享内存/信号量失败 | `privileged` 未开或 `shm_size` 太小 | 检查 6.2 两项 |
| `init_db.py` 报认证失败 | 管理员写成 `omm`（开发机习惯） | 官方镜像用 **`gaussdb`** |
| 后端报 `database compatibility is 'A'` | 建库漏 `DBCOMPATIBILITY 'PG'` | 6.4 重建后再跑迁移 |
| 中文写入失败 | 编码不是 UTF8 | 用 `ENCODING 'UTF8' TEMPLATE template0` 重建 |
| 内存被占满、vLLM OOM | openGauss 按可见内存自动估算 | 6.6 限制 `max_process_memory`/`shared_buffers` |
| 外部能连上 15432 | `ports` 写成 `15432:5432` | 改 `127.0.0.1:15432:5432` 并重启 |
| 若改用 enmotech 镜像，多出库 `omm` | 该镜像 `GS_DB` 默认值不是 postgres | 显式 `GS_DB: postgres`（本文用官方镜像，不涉及） |

## 7. Apache IoTDB 生产部署

### 7.1 形态选择

| 形态 | 适用 | 本文建议 |

| 二进制 all-bin + aarch64 JDK 21 | 需要精确控制 JVM 内存，或现场禁止该容器 | 备选，见 7.8 |

容器镜像已含 arm64 manifest；二进制包是 Java 实现、跨架构，只要 JDK 是 aarch64 即可。

### 7.2 编排文件（IoTDB 段）

并入 `/opt/mes/db/docker-compose.yml`：

```yaml
  iotdb:
    image: apache/iotdb:2.0.11-standalone
    container_name: industrial-ai-iotdb
    hostname: iotdb
    restart: unless-stopped
    ports:
      - "127.0.0.1:6667:6667"           # 只有 SQL 端口对外（且仅回环）
    environment:
      - cn_internal_address=iotdb
      - cn_internal_port=10710
      - cn_consensus_port=10720
      - cn_seed_config_node=iotdb:10710
      - dn_rpc_address=0.0.0.0           # 容器内监听全部，宿主只映射回环
      - dn_internal_address=iotdb
      - dn_rpc_port=6667
      - dn_internal_port=10730
      - dn_mpp_data_exchange_port=10740
      - dn_schema_region_consensus_port=10750
      - dn_data_region_consensus_port=10760
      - dn_seed_config_node=iotdb:10710
    volumes:
      - mes-iotdb-data:/iotdb/data
      - mes-iotdb-logs:/iotdb/logs
    healthcheck:
      test: ["CMD-SHELL", "bash -c 'echo > /dev/tcp/127.0.0.1/6667'"]
      interval: 10s
      timeout: 5s
      retries: 30
      start_period: 60s
```

> 这是 `services.iotdb` 段；顶层 `volumes:` 见 14.6。

要点：

- 容器内 `dn_rpc_address=0.0.0.0` 是必须的（否则宿主映射不通）；对外暴露由 compose
  的 `127.0.0.1:6667:6667` 控制，两者不矛盾。
- 10710~10760 只在容器内部，**不要**加端口映射。
- ConfigNode/DataNode 在同一容器内，启动顺序由镜像 entrypoint 处理；不要用

### 7.8 备选：二进制部署（aarch64）

仅在容器方案不可用、或必须精确控制 JVM 内存时使用。JDK 必须是 **aarch64**。

```bash
# 1) JDK 21（aarch64）
curl -fL -o /tmp/jdk21.tar.gz \
  "https://mirrors.tuna.tsinghua.edu.cn/Adoptium/21/jdk/aarch64/linux/OpenJDK21U-jdk_aarch64_linux_hotspot_21.0.13_9.tar.gz"
mkdir -p /opt/mes/iotdb/jdk21
tar -xzf /tmp/jdk21.tar.gz -C /opt/mes/iotdb/jdk21 --strip-components=1

# 2) IoTDB 2.0.11 all-bin（先校验 SHA-512），解压时保留可执行位
python3 - <<'PY'
import os, zipfile
src, dst = "/tmp/apache-iotdb-2.0.11-all-bin.zip", "/opt/mes/iotdb"
with zipfile.ZipFile(src) as zf:
    zf.extractall(dst)
    for i in zf.infolist():
        if i.is_dir(): continue
        m = (i.external_attr >> 16) & 0o7777
        if m:
            try: os.chmod(os.path.join(dst, i.filename), m)
            except OSError: pass
PY

# 3) 关键配置
cd /opt/mes/iotdb/apache-iotdb-2.0.11-all-bin
sed -i -E 's/^MEMORY_SIZE=.*/MEMORY_SIZE=1G/' conf/confignode-env.sh
sed -i -E 's/^MEMORY_SIZE=.*/MEMORY_SIZE=4G/' conf/datanode-env.sh
sed -i -E 's/^dn_rpc_address=.*/dn_rpc_address=0.0.0.0/' conf/iotdb-system.properties
grep -q preferIPv4Stack conf/datanode-env.sh || \
  echo 'IOTDB_JVM_OPTS="${IOTDB_JVM_OPTS:-} -Djava.net.preferIPv4Stack=true"' >> conf/datanode-env.sh

# 4) 启动（必须 setsid 脱离）
export JAVA_HOME=/opt/mes/iotdb/jdk21
export IOTDB_HOME=$PWD
setsid nohup bash sbin/start-confignode.sh > logs/console-confignode.out 2>&1 < /dev/null &
for i in $(seq 1 60); do ss -ltn | grep -q ':10710\b' && break; sleep 2; done
sleep 3
setsid nohup bash sbin/start-datanode.sh > logs/console-datanode.out 2>&1 < /dev/null &
for i in $(seq 1 45); do ss -ltn | grep -q ':6667\b' && break; sleep 2; done
```

再用 systemd 管理（`/etc/systemd/system/mes-iotdb.service`，`Restart=on-failure`），
否则整机重启后不会自启。开发机文档里有完整的启停脚本可参考。

### 7.9 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 容器反复重启，6667 不通 | 环境变量缺项 | 用完整清单（7.2） |
| 宿主连不上 6667 | 容器内绑 127.0.0.1，或端口映射写错 | 容器内 `0.0.0.0` + 宿主 `127.0.0.1:6667:6667` |
| `SHOW CLUSTER` 节点异常 | 数据卷残留旧集群元数据 | 停服后清空 `mes-iotdb-data` 重来（确认可丢） |
| 改口令后后端连不上 | 没同步 `.env` | 改 `IOTDB_PASSWORD` 并重启后端 |
| 数据卷占满 | 未设 TTL/未归档 | 按 11.5 规划留存与告警 |
| 二进制方式重启不自启 | 未配 systemd | 7.8 的 systemd 单元 |

### 8.6 认证硬化（建议）

Milvus 默认免认证。生产建议开启，并与后端 `MILVUS_TOKEN` 联动：

1. 编辑 `/opt/mes/db/milvus/user.yaml`：

```yaml

  security:
    authorizationEnabled: true
```

2. `docker compose up -d milvus` 重建容器（数据卷不动）；
3. 用默认 `root/Milvus` 登录并改口令（pymilvus）：

```python
from pymilvus import MilvusClient
c = MilvusClient(uri="http://127.0.0.1:19530", token="root:Milvus")
c.update_password(user_name="root", old_password="Milvus", new_password="<MILVUS_ROOT_PASSWORD>")
```

4. 验证免口令被拒、带口令可用：

```bash

  -H 'Content-Type: application/json' -d '{"dbName":"default"}'
# 期望鉴权错误

curl -s -X POST http://127.0.0.1:19530/v2/vectordb/collections/list \
  -H 'Authorization: Bearer root:<MILVUS_ROOT_PASSWORD>' \
  -H 'Content-Type: application/json' -d '{"dbName":"default"}'
# 期望 code=0
```

5. 在 `/etc/mes/compute-service.env` 设置 `MILVUS_TOKEN=root:<MILVUS_ROOT_PASSWORD>`。

> 认证开启后，`build_knowledge.py`、`check.py` 与后端都要用同一 token。
> 该步骤**未在开发机验证**（开发机 v3.0.5 免认证），实施前先在测试容器验证一遍。

### 8.7 知识库初始化

```bash

.venv/bin/python scripts/build_knowledge.py activate <version>   # 切换/回滚
```

关键约定（来自仓库代码，生产必须一致）：

- 集合名：`<KB_NAME>__<version>`，例如 `nuclear_kb__mes_2026_11_16`；
- 向量维度：`EMBEDDING_DIMENSIONS`（默认 1024），**与 Embedding 模型输出一致**；
- 索引：HNSW + **COSINE**；
- 元数据：`kb.meta` 记录 embedding 模型与维度，维度不一致会拒绝检索；
- 换模型/换维度 = 必须重建集合，不能原地改。

```bash

```

重建产出的版本号不同，注意 `activate` 到正确版本。

### 8.9 若改用外置 etcd/MinIO

只有必须把元数据/对象存储独立出去时才做，需要额外镜像（均已核实含 arm64）：

| 镜像 | digest |
| --- | --- |
| `quay.io/coreos/etcd:v3.5.25` | `sha256:52f17f7e56e4f7239f0320dbfcbcc24721163d7d78ae710b466af3254ccf6366` |
| `milvusdb/minio:RELEASE.2024-12-18T13-15-44Z` | `sha256:1dce27c494a16bae114774f1cec295493f3613142713130c2d22dd5696be6ad3` |

改为独立组件后，`ETCD_USE_EMBED` 置 `false`，`COMMON_STORAGETYPE` 改 `minio`，
端口一律只绑回环，并给 MinIO 配强口令。**默认不建议**。

### 8.10 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `no matching manifest for linux/arm64` | 镜像无 arm64，或拉了 amd64 包 | 换有 arm64 的 tag；重导镜像 |
| `exec format error` | 导入了错误架构的 tar | `docker image inspect ... Architecture` 应为 arm64 |
| standalone 起不来，日志 Permission denied | 挂载权限或 SELinux | 检查 `:ro` 文件权限；SELinux 加 `:z` |
| `healthz` 一直不 OK | 首次初始化慢，或内嵌 etcd 起不来 | 等满 180s；看 `docker compose logs milvus` |
| 后端检索报集合不存在 | 未跑 `build_knowledge.py`，或 `KB_NAME` 不一致 | 构建知识库，核对集合名 |
| 检索报维度不一致 | `EMBEDDING_DIMENSIONS` 与建库时不同 | 重建集合（8.7） |
| 端口被外部访问 | `ports` 未绑 `127.0.0.1` | 立即改绑定并重启，按 5.1 复核 |

### 11.5 容量规划

- 时序（IoTDB）是主增长项：先估算"站数 × 设备数 × 每设备测点数 × 采样频率 ×
  每条记录字节 × 留存天数"，再乘 1.5 安全系数；
- 向量（Milvus）：`切片数 × 维度 × 4 字节 ×（1 + 索引系数）`，HNSW 按 1.5~2 倍估；
- 会话（openGauss）：按每会话消息数 × 平均长度估，通常远小于前两者；
- 备份目录单独估：约为对应库大小的 1~2 倍。

## 12. 故障排查（含 ARM64 专有项）

### 12.1 排查顺序

```text
镜像架构 → 镜像是否存在 → 容器是否启动 → 端口是否监听 → 库是否 healthy
→ 认证/权限 → 数据/编码 → 后端配置 → 网络/防火墙
```

### 12.2 ARM64 与镜像类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `no matching manifest for linux/arm64/v8 in the manifest list entries` | 镜像无 arm64，或拉的是 amd64-only tag | 换含 arm64 的 tag（本文三镜像均已核实含 arm64）；或现场自建 arm64 镜像 |
| `exec format error` / 容器秒退 | 导入的是 amd64 tar | `docker image inspect <img> --format '{{.Architecture}}'` 必须 `arm64`，重导 |
| `docker load` 后 tag 丢失 | save 的是 digest 引用或未带 tag | `docker save <tag>` 时显式写 tag；load 后 `docker images` 核对 |
| `docker info` 显示 amd64 | 宿主不是 ARM64，或装错 Docker 包 | 先修系统，不要继续 |
| `Permission denied` 挂载配置文件 | SELinux Enforcing | 挂载加 `:z`，或 `chcon`；不要关 SELinux 了事 |

### 12.3 容器与运行类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| openGauss 起不来，报共享内存/sem | 缺 `privileged` 或 `shm_size` 太小 | 6.2 补齐 |
| Milvus 起不来，日志 `Operation not permitted` | 缺 `seccomp:unconfined` | 8.3 |
| Milvus 一直 `starting` | 首次初始化慢 | 等 180s，看日志 |
| 容器重启后数据没了 | 卷名写错或用了 `down -v` | `docker volume ls` 核对；检查 volume `name:` |
| 端口占用 | 宿主已有服务 | `ss -lntp \| grep :15432` 定位 |
| 时间不对 | 未设时区/chrony | 环境手册第 1 章 |

### 12.4 openGauss 类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `GS_PASSWORD is not meet requirements` | 复杂度/含用户名 | 4.3 + `down -v` 重建 |
| 管理员认证失败 | 用了 `omm` | 官方镜像用 `gaussdb` |
| `database compatibility is 'A'` | 建库漏 `DBCOMPATIBILITY 'PG'` | 6.4 重建 |
| 中文写不进 | 库编码非 UTF8 | 6.4 重建 |
| 连接数打满 | `max_connections` 偏小/连接泄漏 | 查 `pg_stat_activity`，调参或修后端 |
| 内存暴涨 | 自动估算共享内存 | 6.6 限制 |

### 12.5 IoTDB 类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 6667 不通 | 绑定/端口映射 | 7.2 |
| `SHOW CLUSTER` 异常 | 数据卷残留旧元数据 | 7.9 |
| 序列不存在 | 没跑 `init_db.py --only iotdb` | 9.2 |
| 写作水位线不前进 | 后端 MQTT 入库链路问题（非库本身） | 查后端与 MQTT |

### 12.6 Milvus 类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| healthz 不 OK | 初始化慢/内嵌 etcd 异常 | 8.4/8.10 |
| 集合不存在 | 未建库或 `KB_NAME` 不符 | 8.7 |
| 维度不一致 | Embedding 维度变了 | 重建集合 |
| 认证失败 | token 格式/未同步 | `MILVUS_TOKEN=user:password`，三处一致 |

### 12.7 数据与备份类

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 备份文件 0 字节 | `gs_dump` 失败但未检查退出码 | 重跑并校验文件大小/SQL 头 |
| 恢复后表不全 | 恢复到错误 schema/库 | 用同名库、同 owner |
| 冷备恢复后库起不来 | 解包属主不对 | `tar -p` 或 root 解包，保持原属主 |

## 13. 回退与迁移

### 13.1 回退原则

- **镜像**：回退 = 改回旧 tag/digest + `up -d`，旧镜像保留在 `/data/pkg/images`；
- **数据**：破坏性操作前必须备份；恢复 = 停容器 → 还原卷/导入 dump → 起容器；
- **配置**：`/opt/mes/db` 与 `/etc/mes` 纳入版本管理（git 或离线包），改前先备份。

### 13.2 三库的回退边界

| 库 | 可回退 | 不可逆点 |
| --- | --- | --- |
| openGauss | 镜像回退 + 备份还原 | 迁移脚本已执行（版本只增不减） |
| IoTDB | 镜像回退 + 冷备还原 | 数据卷被覆盖 |
| Milvus | 镜像回退 + 冷备/重建 | 跨大版本升级后的存储格式 |

Milvus 跨大版本（如 2.6 → 3.x）**不要**直接换镜像，按官方迁移工具/文档走，且必须先备份。

### 13.3 迁移到新机

1. 新机按环境配置手册装好系统基线；
2. 按本文第 2~4 章准备（镜像可用同一批 tar）；
3. 停旧机三库 → 冷备三个 volume + `gs_dump` → 传到新机；
4. 新机起 compose（用同名 volume）→ 还原；
5. 改后端 `.env` 指向新机（同机则不用）→ `check.py` 验收。

### 14.6 完整 compose 文件（可直接落地）
