# ARM64 双服务器与 Electron 部署指南

> 适用范围：A 主服务器、B 算力服均运行 ARM64 银河麒麟 Linux；前端最终以 Electron
> 应用运行在 Windows 用户电脑。
>
> 编写基线：仓库 `2026-11-16` 当前实现。
>
> 运行身份：现场只使用 root，A/B 服务均以 root 运行。
>
> 相关文档：[需求文档](./需求文档.md)、[设计文档](./设计文档.md)、
> [本地部署模型调用指南](./本地部署模型调用指南.md)。

## 1. 目标与部署结论

推荐采用以下边界：

- Windows 用户电脑只访问 A 主服务器，不直接访问 B 算力服。
- A 上的 Go `main_server` 和 B 上的 FastAPI 都只监听回环地址。
- A、B 各使用 Nginx 作为 HTTPS 入口；A 对用户网段开放，B 只对 A 开放。
- Electron 页面资源保存在用户电脑，API 请求通过 A 的稳定域名进入。
- A 调用 B 时使用内部 CA 签发的 HTTPS 证书；当前 B 未启用 API Key，后续启用时由 A 注入
  独立服务令牌。
- vLLM、Milvus、IoTDB、openGauss、Embedding 等能力只在 B 本机或容器内部访问。

最终访问关系：

```text
Windows Electron
  └─ HTTPS 443 ──> A Nginx
                     └─ HTTP 127.0.0.1:8080 ──> Go main_server
                                                   └─ HTTPS 8443 ──> B Nginx
                                                                       └─ HTTP
                                                                          127.0.0.1:8000
                                                                          ──> FastAPI
```

业务请求示例：

```text
Electron:
  https://mes-gateway.plant.local/api/v1/assistant/chat

A Go 主服务到 B:
  https://compute.plant.local:8443/api/v1/chat

A 和 B 的应用监听:
  A: 127.0.0.1:8080
  B: 127.0.0.1:8000
```

## 2. 现场信息与占位符

本文使用下列示例值，部署时必须替换为现场网络规划：

| 项目 | 示例值 | 说明 |
| --- | --- | --- |
| A 主服务器 IP | `192.168.50.10` | 用户网段可访问 |
| B 算力服 IP | `192.168.50.20` | 只允许 A 访问 |
| Windows 网段 | `192.168.50.0/24` | 建议进一步缩小 |
| A 对外域名 | `mes-gateway.plant.local` | 用户端 API 入口 |
| B 内部域名 | `compute.plant.local` | A 访问 B 的入口 |
| A 入口端口 | `443/tcp` | 对用户网段开放 |
| B 内部入口端口 | `8443/tcp` | 只对 A 开放 |
| Go 监听端口 | `8080/tcp` | 仅 A 本机 |
| FastAPI 监听端口 | `8000/tcp` | 仅 B 本机 |

### 2.1 文档中的机器信息

需求文档和设计文档已明确 B 算力服的基线：

- CPU：鲲鹏 920-Smart，32 核。
- 内存：128 GB DDR4 2933。
- 存储：4 TB M.2。
- 推理加速：昇腾 Atlas 300I A2 64 GB × 1。
- 架构：ARM64。
- 模型：Qwen3-30B-A3B W8A8；预测维护解释层允许 Qwen3-14B 或压测通过的等价模型。
- 应用：Python + FastAPI，优先部署 ARM64 容器镜像。

文档没有给出 A 的具体 CPU、内存规格，只要求主服务器和算力服使用独立主机。因此不能在
未核实的情况下假设 A 的磁盘、内存或数据库部署方式。

部署前在 A、B 分别执行：

```bash
cat /etc/os-release
uname -m
getconf LONG_BIT
```

A、B 均应得到 `aarch64` 和 `64`。如果得到 `x86_64`，不要继续使用本指南中的 ARM64
构建产物，应重新构建对应架构版本。

### 2.2 当前实现限制

本指南按当前代码编写，部署前必须了解以下限制：

1. Go `main_server` 当前只代理智能助手聊天接口
   `POST /api/v1/assistant/chat`，不是通用反向代理。
2. `main_server` 的 `/readyz` 只表示 Go 进程自身就绪，不探测 B 或模型服务。
3. `main_server` 不托管前端静态文件，不适合作为 Electron 页面服务器。
4. `main_server` 只读取运行时 JSON 配置，不读取环境变量或 `.env`；systemd 通过
   `-config` 参数指定配置文件。
5. Go 主服务当前没有 CORS 中间件。Electron 打包后不能从 `file://` 页面直接跨域请求 A。
6. 当前 `backend/deploy/docker-compose.yml` 是本地开发编排，包含开发密码、匿名 MQTT
   和对外映射端口，不能原样用于生产。
7. 当前仓库没有生产用 ARM64 Dockerfile、Nginx 配置、Electron 打包配置或本地 API 网关。
8. `backend` 当前没有 `backend/.env.example`，配置变量应以 `backend/app/config.py` 和本文为准。
9. FastAPI 聊天接口是 SSE，A、B 两级 Nginx 都必须关闭响应缓冲。
10. 当前维护页面尚未全部接入真实业务 API；后续增加接口时，必须同步修改 A 主服务路由。

## 3. 网络、端口和访问控制

### 3.1 端口规划

| 来源 | 目标 | 端口 | 用途 | 开放范围 |
| --- | --- | --- | --- | --- |
| Windows Electron | A Nginx | `443` | 用户 API | 用户网段 |
| A | B Nginx | `8443` | 主服务调用算力服 | 仅 A IP |
| A 本机 | Go main_server | `8080` | Nginx 上游 | 仅回环 |
| B 本机 | FastAPI | `8000` | Nginx 上游 | 仅回环 |
| B 本机 | vLLM | 示例 `8001` | 模型推理 | 仅回环或容器网络 |
| B 本机 | Embedding | 示例 `8002` | 向量化 | 仅回环或容器网络 |
| B 本机 | Milvus | `19530`、`9091` | 向量库 | 仅回环或容器网络 |
| B 本机 | IoTDB | `6667` | 时序数据 | 仅回环或容器网络 |
| B 本机 | openGauss | 示例 `15432` | 会话与业务数据 | 仅回环或容器网络 |
| B 本机 | MQTT | 示例 `1883/8883` | 数据接入 | 受控内网 |

A 不得向用户网段开放 `8080`。B 不得向用户网段开放 `8000`、`8443`、模型端口或数据库
端口。B 的 `8443` 只允许 A 的地址。

### 3.2 DNS 或 hosts

生产和准生产环境优先配置内部 DNS：

```text
mes-gateway.plant.local  -> 192.168.50.10
compute.plant.local      -> 192.168.50.20
```

没有内部 DNS 时，可临时配置 hosts。

Windows 管理员 PowerShell：

```powershell
Add-Content `
  -Path "$env:SystemRoot\System32\drivers\etc\hosts" `
  -Value "192.168.50.10 mes-gateway.plant.local"
```

A：

```bash
echo "192.168.50.20 compute.plant.local" | sudo tee -a /etc/hosts
```

使用域名而不是直接写 IP 的原因：

- 后续更换 A/B 地址时不必重新打包 Electron。
- TLS 证书可以绑定稳定域名。
- Go 的证书校验不会因 IP 变化失效。

### 3.3 内部 CA 和服务器证书

建议建立一个单位内部 CA，为 A、B 分别签发带 SAN 的服务端证书。不要把 CA 私钥放在 A 或 B
的业务部署目录中，CA 私钥应离线保存。

下面的命令仅用于说明证书要求，正式证书应由单位证书系统签发：

```bash
mkdir -p /secure/ca
cd /secure/ca

openssl genrsa -out mes-ca.key 4096
openssl req -x509 -new -nodes \
  -key mes-ca.key \
  -sha256 \
  -days 3650 \
  -subj "/CN=MES Internal Root CA" \
  -out mes-ca.crt
```

A 证书扩展文件：

```ini
# mes-gateway.ext
basicConstraints = CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:mes-gateway.plant.local, IP:192.168.50.10
```

B 证书扩展文件：

```ini
# compute-service.ext
basicConstraints = CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:compute.plant.local, IP:192.168.50.20
```

将上面的扩展内容分别保存为 `mes-gateway.ext` 和 `compute-service.ext`，然后签发证书：

```bash
cd /secure/ca

# A 主服务器证书
openssl genrsa -out mes-gateway.key 2048
openssl req -new \
  -key mes-gateway.key \
  -subj "/CN=mes-gateway.plant.local" \
  -out mes-gateway.csr

openssl x509 -req \
  -in mes-gateway.csr \
  -CA mes-ca.crt \
  -CAkey mes-ca.key \
  -CAcreateserial \
  -days 825 \
  -sha256 \
  -extfile mes-gateway.ext \
  -out mes-gateway.crt

# B 算力服证书
openssl genrsa -out compute-service.key 2048
openssl req -new \
  -key compute-service.key \
  -subj "/CN=compute.plant.local" \
  -out compute-service.csr

openssl x509 -req \
  -in compute-service.csr \
  -CA mes-ca.crt \
  -CAkey mes-ca.key \
  -CAserial mes-ca.srl \
  -days 825 \
  -sha256 \
  -extfile compute-service.ext \
  -out compute-service.crt
```

验证证书链和 SAN：

```bash
openssl verify -CAfile mes-ca.crt mes-gateway.crt
openssl verify -CAfile mes-ca.crt compute-service.crt

openssl x509 -in mes-gateway.crt -noout -text \
  | grep -A1 "Subject Alternative Name"
openssl x509 -in compute-service.crt -noout -text \
  | grep -A1 "Subject Alternative Name"
```

签发后的部署文件：

```text
A:
  /etc/mes/tls/mes-gateway.crt
  /etc/mes/tls/mes-gateway.key
  /etc/mes/tls/mes-ca.crt

B:
  /etc/mes/tls/compute-service.crt
  /etc/mes/tls/compute-service.key
  /etc/mes/tls/mes-ca.crt
```

文件权限：

```bash
sudo chmod 0755 /etc/mes/tls
sudo chmod 0644 /etc/mes/tls/*.crt
sudo chmod 0600 /etc/mes/tls/*.key
```

Windows 用户电脑需要信任同一内部 CA。通过“受信任的根证书颁发机构”导入
`mes-ca.crt`。Electron 主进程如果使用 Node 的 HTTPS 客户端，还应显式加载 CA：

```powershell
$env:NODE_EXTRA_CA_CERTS = "C:\Program Files\SWFH-MES\certs\mes-ca.crt"
```

不得通过以下方式绕过证书错误：

- Electron `webSecurity: false`
- Node `rejectUnauthorized: false`
- Vite `secure: false`
- Go 自定义跳过 TLS 校验

## 4. A 主服务器部署

### 4.1 构建 ARM64 Go 程序

可以在 Windows 开发机交叉编译，也可以在 ARM64 Linux 构建：

```powershell
cd D:\project\SWFH-26-122Agent\main_server

# 先在当前 Windows 架构上完成测试，避免随后生成 Linux 测试程序后无法执行
go test ./...

$env:GOOS = "linux"
$env:GOARCH = "arm64"
$env:CGO_ENABLED = "0"

go build -trimpath -ldflags="-s -w" -o bin/main-server .

Remove-Item Env:GOOS
Remove-Item Env:GOARCH
Remove-Item Env:CGO_ENABLED
```

检查产物：

```powershell
Get-FileHash .\bin\main-server -Algorithm SHA256
```

确认文件格式：

```bash
file main-server
```

应显示 ARM aarch64、64-bit 和 Linux ELF。发布时同时记录：

- Git 提交号。
- Go 版本。
- 二进制 SHA-256。
- 配置文件模板版本。

### 4.2 目录和运行身份

```bash
sudo mkdir -p \
  /opt/mes/main-server/releases \
  /opt/mes/main-server/bin \
  /etc/mes
```

上传产物后：

```bash
sudo install -d -o root -g root -m 0755 \
  /opt/mes/main-server/releases/0.1.0

sudo install -o root -g root -m 0755 \
  main-server \
  /opt/mes/main-server/releases/0.1.0/main-server

sudo ln -sfn \
  /opt/mes/main-server/releases/0.1.0 \
  /opt/mes/main-server/current
```

最终结构应为：

```text
/opt/mes/main-server/
├─ current -> releases/0.1.0
└─ releases/
   └─ 0.1.0/
      └─ main-server
```

systemd 指向 `/opt/mes/main-server/current/main-server`。

### 4.3 A 运行时配置

创建 `/etc/mes/main-server.json`：

```json
{
  "listen_addr": "127.0.0.1:8080",
  "environment": "production",
  "log_level": "info",
  "shutdown_timeout": "10s",
  "compute": {
    "base_url": "https://compute.plant.local:8443",
    "chat_path": "/api/v1/chat",
    "timeout": "3m",
    "api_key": ""
  }
}
```

权限：

```bash
sudo chown root:root /etc/mes/main-server.json
sudo chmod 0600 /etc/mes/main-server.json
```

说明：

- `listen_addr` 保持回环地址，由 Nginx 对外转发。
- `compute.base_url` 只填写算力服基础地址，不包含聊天接口路径。
- `compute.chat_path` 当前为 `/api/v1/chat`；B 的接口路径变化时只修改该字段。
- `compute.timeout` 必须覆盖一次完整 SSE 分析所需时间。
- 当前 B 未启用 API Key，因此 `compute.api_key` 为空；若后续启用，A 和 B 必须配置相同令牌。
- 浏览器和 Electron 不应持有该密钥。
- 修改配置后重启服务，不支持热加载。

### 4.4 A systemd 服务

创建 `/etc/systemd/system/mes-main-server.service`：

```ini
[Unit]
Description=MES main server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=root
Group=root
ExecStart=/opt/mes/main-server/current/main-server -config /etc/mes/main-server.json
Restart=on-failure
RestartSec=2
TimeoutStopSec=20
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true
ProtectSystem=strict

[Install]
WantedBy=multi-user.target
```

启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now mes-main-server
sudo systemctl status mes-main-server
```

检查本机 API：

```bash
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
curl --fail http://127.0.0.1:8080/api/v1/system/info
```

`/readyz` 返回成功只说明 Go 主服务自身启动成功，不表示 B 可用。

### 4.5 A Nginx

安装 Nginx：

```bash
sudo dnf install -y nginx
```

如果使用离线环境，应通过现场软件源或受控制品库安装 ARM64 RPM。不要混用 x86_64 RPM。

创建 `/etc/nginx/conf.d/mes-gateway.conf`：

```nginx
server {
    listen 443 ssl http2;
    server_name mes-gateway.plant.local;

    server_tokens off;

    ssl_certificate     /etc/mes/tls/mes-gateway.crt;
    ssl_certificate_key /etc/mes/tls/mes-gateway.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:MES_TLS:20m;
    ssl_session_timeout 10m;

    client_max_body_size 128k;

    # 可选：在 Nginx 层再限制用户网段
    allow 192.168.50.0/24;
    deny all;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        # SSE 聊天接口不能缓存或缓冲
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_cache off;
        gzip off;

        proxy_connect_timeout 5s;
        proxy_read_timeout    240s;
        proxy_send_timeout    240s;
    }

    location = /healthz {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Connection "";
    }

    location = /readyz {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Connection "";
    }

    # Electron 页面资源在用户本机，A 不提供静态页面
    location / {
        return 404;
    }
}
```

检查并启动：

```bash
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

如果现场要求 HTTP 自动跳转 HTTPS，可以增加：

```nginx
server {
    listen 80;
    server_name mes-gateway.plant.local;
    return 301 https://$host$request_uri;
}
```

禁用 HSTS，直到确认所有客户端都长期使用 HTTPS；否则证书配置错误时难以回退。

### 4.6 A 防火墙

使用 `firewalld` 时：

```bash
sudo firewall-cmd --permanent \
  --add-rich-rule='rule family="ipv4" source address="192.168.50.0/24" port port="443" protocol="tcp" accept'

sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

如果前端开发机地址固定，优先只开放该地址：

```bash
sudo firewall-cmd --permanent \
  --add-rich-rule='rule family="ipv4" source address="192.168.50.100" port port="443" protocol="tcp" accept'
```

确认 `8080` 没有对外监听：

```bash
sudo ss -lntp | grep -E ':(443|8080)\b'
```

期望：

- Nginx 监听 `0.0.0.0:443` 或指定网卡地址。
- Go 只监听 `127.0.0.1:8080`。

### 4.7 A 信任 B 的证书

将内部 CA 安装到 A 的系统信任库。银河麒麟通常属于 RPM 系：

```bash
sudo cp mes-ca.crt /etc/pki/ca-trust/source/anchors/mes-ca.crt
sudo update-ca-trust
```

如果现场系统使用 Debian 风格信任库：

```bash
sudo cp mes-ca.crt /usr/local/share/ca-certificates/mes-ca.crt
sudo update-ca-certificates
```

Go 使用系统根证书。CA 安装完成后重启主服务：

```bash
sudo systemctl restart mes-main-server
```

从 A 验证 B：

```bash
curl --fail \
  --cacert /etc/mes/tls/mes-ca.crt \
  https://compute.plant.local:8443/api/v1/health
```

当前 B 未启用 API Key，因此不发送 `X-API-Key`。如果后续启用，需要在
`/etc/mes/main-server.json` 的 `compute.api_key` 和 B 的 `API_KEY` 中配置相同值。

## 5. B 算力服部署

### 5.1 B 的前置条件

```bash
uname -m
uv --version
uv python find 3.12
docker --version
docker compose version
```

要求：

- `uname -m` 为 `aarch64`。
- `uv` 可用，并且 `uv python find 3.12` 能找到 Python 3.12。
- 容器镜像必须是 ARM64。
- 所有基础镜像、Python wheel、模型、Embedding 模型和知识制品可离线导入。

需要准备的制品：

- FastAPI 应用发布包或 ARM64 镜像。
- Python ARM64 依赖 wheelhouse。
- Qwen3 模型权重。
- Embedding/Rerank 模型。
- vLLM-Ascend、CANN 和驱动组件。
- 固定知识语料及发布清单。
- IoTDB、Milvus、openGauss、MQTT 镜像或现场已有服务信息。

模型启动命令必须依据实际 CANN、驱动、vLLM-Ascend 和模型版本确认。参见
[本地部署模型调用指南](./本地部署模型调用指南.md)，不要把未经压测的命令直接用于生产。

### 5.2 B 目录

```bash
sudo mkdir -p \
```

### 5.3 Python 环境

在 B 上使用 uv 创建虚拟环境。若依赖通过本地 wheelhouse 提供：

```bash
cd /opt/mes/backend/current
env \
  UV_PYTHON_INSTALL_DIR=/opt/uv/python \
  uv venv --python 3.12 .venv

env \
  UV_PYTHON_INSTALL_DIR=/opt/uv/python \
  UV_NO_INDEX=1 \
  UV_FIND_LINKS=/opt/mes/wheels \
  uv sync --frozen --no-dev --extra mqtt --extra pdf
```

生产运行环境不需要安装 `dev` 依赖。安装后先执行基本导入：

```bash
.venv/bin/python -c "import app.main"
```

自动化测试应在独立的构建/测试环境执行，避免把 `pytest` 等开发依赖带入生产虚拟环境：

```bash
# 仅在构建/测试环境执行
env \
  UV_PYTHON_INSTALL_DIR=/opt/uv/python \
  UV_PROJECT_ENVIRONMENT=.venv-test \
  UV_NO_INDEX=1 \
  UV_FIND_LINKS=/opt/mes/wheels \
  uv sync --frozen --extra dev --extra mqtt --extra pdf
.venv-test/bin/pytest -q
```

如果某个依赖只有 x86_64 wheel，应立即停止发布。不得在 ARM64 机器上强行安装错误架构的
二进制包，也不得依赖公网临时下载。

当前仓库没有生产 Dockerfile。如果采用容器部署，需要在 B 的 ARM64 环境或受控构建环境中
新增并验证 Dockerfile，再把镜像离线导入 B。FastAPI 直接运行在 B 的主机 Python 虚拟环境中
也是可行的过渡方案。

### 5.4 B 数据服务

当前 [docker-compose.yml](../../backend/deploy/docker-compose.yml) 只适合本地开发：

- IoTDB、Milvus、openGauss 和 Mosquitto 端口默认映射到所有网卡。
- openGauss 使用开发密码。
- Mosquitto 允许匿名且未启用 TLS。

生产部署至少要做以下调整：

1. 修改所有开发密码。
2. 将数据库和 Milvus 端口绑定到 `127.0.0.1`，或使用独立 Docker 网络。
3. MQTT 启用认证、TLS 和主题级 ACL。
4. 使用持久化卷并配置备份。
5. 固定镜像版本和 SHA-256。
6. 使用 ARM64 镜像。

仅做主机端口绑定时的生产覆盖示例：

```yaml
# 示例，不是当前已存在的生产文件
services:
  iotdb:
    ports:
      - "127.0.0.1:6667:6667"

  milvus:
    ports:
      - "127.0.0.1:19530:19530"
      - "127.0.0.1:9091:9091"

  opengauss:
    ports:
      - "127.0.0.1:15432:5432"

  mosquitto:
    ports:
      - "127.0.0.1:1883:1883"
```

如果 FastAPI 也运行在容器中，应通过 Docker 网络使用服务名，而不是经过宿主机回环地址。

### 5.5 B 环境配置

FastAPI 会读取工作目录下的 `.env`。建议文件：

```text
/etc/mes/compute-service.env
```

虽然当前代码也支持工作目录下的 `.env`，但生产环境推荐由 systemd
`EnvironmentFile` 注入，避免升级前端发布目录时覆盖配置。

最小示例：

```ini
APP_ENV=production
LOG_LEVEL=INFO
API_KEY=

# FastAPI 自身的监听地址由启动参数控制
# 生产环境不开放 /docs

# 时序数据库
TIMESERIES_BACKEND=iotdb
IOTDB_HOST=127.0.0.1
IOTDB_PORT=6667
IOTDB_USER=替换用户名
IOTDB_PASSWORD=替换强密码
IOTDB_ROOT=root.mes

# openGauss；为空时会话只保存在内存，生产不建议
OPENGAUSS_DSN="host=127.0.0.1 port=15432 dbname=industrial_ai user=app_ai password=替换强密码"

# 本地模型。注意不要与 FastAPI 的 8000 端口冲突
LLM_PROVIDER=vllm
LLM_BASE_URL=http://127.0.0.1:8001/v1
LLM_MODEL=替换为实际 served-model-name
LLM_TIMEOUT_SECONDS=180

# 本地 Embedding；端口示例，按实际服务修改
EMBEDDING_PROVIDER=local
EMBEDDING_BASE_URL=http://127.0.0.1:8002/v1
EMBEDDING_MODEL=替换为实际模型
EMBEDDING_DIMENSIONS=1024

# Milvus / 知识库
MILVUS_URI=http://127.0.0.1:19530
KB_NAME=nuclear_kb

# 生产不使用进程内模拟
DEMO_SIMULATION=false

# A 通过服务端调用 B，不使用浏览器 CORS
CORS_ORIGINS=
```

注意事项：

- `APP_ENV=production` 时，后端会拒绝使用公网 DeepSeek 和智谱 Embedding，应切换为本地
  模型和本地 Embedding。
- 当前 B 未启用 API Key，`API_KEY` 保持为空；若后续启用，必须和 A 的
  `compute.api_key` 相同。
- `LLM_BASE_URL` 不能配置成 FastAPI 自己的 `127.0.0.1:8000`。
- 生产必须使用 openGauss 或其他持久化会话存储，不能依赖内存会话。
- 真实 MQTT 和数据源稳定后关闭 `DEMO_SIMULATION`。

权限：

```bash
sudo chown root:root /etc/mes/compute-service.env
sudo chmod 0600 /etc/mes/compute-service.env
```

### 5.8 B Nginx

在 B 上安装 ARM64 Nginx。离线环境应使用现场软件源或受控制品库：

```bash

```

创建 `/etc/nginx/conf.d/compute-service.conf`：

```nginx
server {
    listen 8443 ssl http2;
    server_name compute.plant.local;

    server_tokens off;

    ssl_certificate     /etc/mes/tls/compute-service.crt;
    ssl_certificate_key /etc/mes/tls/compute-service.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:COMPUTE_TLS:20m;
    ssl_session_timeout 10m;

    allow 192.168.50.10;
    deny all;

    client_max_body_size 128k;

    location /api/v1/ {
        proxy_pass http://127.0.0.1:8000;

        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-API-Key         $http_x_api_key;
        proxy_set_header X-User-Id         $http_x_user_id;
        proxy_set_header X-Request-ID      $http_x_request_id;
        proxy_set_header Connection        "";

        proxy_buffering off;
        proxy_request_buffering off;
        proxy_cache off;
        gzip off;

        proxy_connect_timeout 5s;
        proxy_read_timeout    240s;
        proxy_send_timeout    240s;
    }

    # 未来增加 /internal/v1/ 时，必须继续只允许 A，并单独审查接口权限
    location / {
        return 404;
    }
}
```


### 5.9 B 防火墙

只允许 A 访问 `8443`：

```bash

  --add-rich-rule='rule family="ipv4" source address="192.168.50.10" port port="8443" protocol="tcp" accept'
```

不得开放：

回环或容器网络。

## 6. Windows Electron 接入

### 6.1 开发阶段

开发时 Electron 由 Vite 提供页面，使用 Vite 代理访问 A，可继续采用同源 `/api`。

将 `frontend/vite.config.ts` 的代理示例改为：

```ts
server: {
  proxy: {
    '/api': {
      target: 'https://mes-gateway.plant.local',
      changeOrigin: true,
    },
  },
},
```

前端配置：

```ini
VITE_API_BASE_URL=/api
```

Windows 开发终端需要信任内部 CA：

```powershell
$env:NODE_EXTRA_CA_CERTS = "C:\certs\mes-ca.crt"
cd D:\project\SWFH-26-122Agent\frontend
npm run dev
```

Vite 代理是 Node 进程，Node 不一定自动使用 Windows“受信任根证书”中的内部 CA，因此
`NODE_EXTRA_CA_CERTS` 很重要。

### 6.2 打包阶段

Electron 正式包应：

- 把 Vite 构建产物打包到应用资源中。
- 不把 A 的 IP、服务令牌或数据库凭据写入渲染进程。
- 不关闭 `webSecurity`、`contextIsolation` 或沙箱。
- 通过 preload 暴露最小 API，不启用 `nodeIntegration`。

当前前端从 `import.meta.env.VITE_API_BASE_URL` 读取 API 地址，这是构建时配置。若现场地址
可能变化，后续应改为 Electron 运行时配置。例如：

```json
{
  "apiBaseUrl": "https://mes-gateway.plant.local/api",
  "chatTimeoutMs": 180000
}
```

配置文件可放在 Electron `app.getPath('userData')` 目录，由主进程读取并通过受限 IPC 提供给
渲染进程。

### 6.3 打包后的 CORS 问题

Electron 使用 `file://` 加载本地页面时，渲染进程直接请求
`https://mes-gateway.plant.local` 属于跨域请求。当前 A 的 Go 主服务没有 CORS 支持，因此会
被 Chromium 拦截。

推荐方案是在 Electron 主进程启动一个仅绑定 `127.0.0.1` 的本地同源网关：

```text
Electron 页面
  http://127.0.0.1:<随机端口>/api/...
        │
        ▼
Electron 主进程本地网关
  https://mes-gateway.plant.local/api/...
```

本地网关应满足：

- 只绑定 `127.0.0.1`。
- 使用随机端口或一次性会话令牌，避免本机其他页面任意调用。
- 不向渲染进程暴露 A 配置中的 `compute.api_key`。
- 透传 SSE，不缓冲响应。
- 使用 `NODE_EXTRA_CA_CERTS` 或显式 CA 验证 A 的证书。

另一种方案是把 API 请求放在 Electron 主进程，通过 preload/IPC 与页面通信。该方案安全边界
更好，但现有 `fetch` 和 SSE 解析代码需要重构。

不建议采用以下方案：

- 在 A 的 Nginx 上配置 `Access-Control-Allow-Origin: *`。
- 允许不可信 Origin 使用服务端令牌。
- 关闭 Electron Web 安全。
- 让 Electron 直接连接 B。

### 6.4 用户身份

当前后端 `X-User-Id` 仅用于识别用户，不是认证凭据。正式接入 MES 登录后：

- Electron 不直接信任用户输入的身份头。
- 用户身份应由 A 主服务器验证 MES 登录令牌后生成。
- A 只把可信的 `X-User-Id` 传给 B。
- B 不直接把 `X-User-Id` 当作服务认证。
- 服务认证仍使用独立 `X-API-Key` 或后续服务令牌。

Linux：

```bash
curl -N \
  --cacert /etc/mes/tls/mes-ca.crt \
```

Windows PowerShell：

```powershell
curl.exe -N `
```

- 首字节不是完整回答一次性返回，而是逐步产生 SSE。

## 10. 故障排查

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| Electron 报证书错误 | 未信任内部 CA、证书 SAN 不匹配 | 导入 CA，检查 SAN 是否包含域名 |
| A Go 报 `x509` | A 未信任 B 的 CA | 安装 CA 到系统信任库并重启服务 |
| A 返回 `502` | B Nginx 不可达、DNS 错误、路径错误 | 从 A 执行 `curl`，检查 B Nginx 和防火墙 |
| A 返回 `504` | 模型超时、B 处理超时 | 检查 `compute.timeout` 和两级 Nginx timeout |
| B 返回 `401` | 后续启用 API Key 后 A/B 值不一致 | 比较 JSON `compute.api_key` 和 B `API_KEY` |
| SSE 一次性返回 | Nginx 开启缓冲 | 两级 Nginx 均关闭 `proxy_buffering` 和 gzip |
| `readyz` 正常但聊天失败 | `/readyz` 不探测 B | 直接检查 B `/api/v1/health` |
| `/api/v1/...` 返回 404 | Go 主服务没有该路由 | 当前只代理 assistant，补齐主服务路由 |
| Electron 报 CORS | `file://` 直接请求 A | 使用本地同源网关或 IPC，不要关闭安全策略 |
| `exec format error` | 镜像或二进制架构错误 | 使用 ARM64/aarch64 产物 |
| FastAPI 启动即报配置错误 | 生产环境仍使用公网模型或缺少 DSN | 使用本地模型，检查 `.env` 和持久化会话 |
| B 健康返回 `503` | IoTDB/openGauss/Milvus/知识库异常 | 查看 `checks`，逐项恢复依赖 |
| B 端口对用户开放 | Compose 端口绑定为 `0.0.0.0` | 改为 `127.0.0.1` 或容器网络并修防火墙 |
| Nginx 返回 `413` | 请求体超过限制 | 检查业务限制，当前 Go 消息体上限为 64 KiB |
| 修改 `main-server.json` 不生效 | 未重启服务或 `-config` 指向错误文件 | 检查 systemd `ExecStart` 并重启服务 |
| Go 启动报配置错误 | 文件缺失、JSON 非法、未知字段、URL、路径或超时非法 | 根据启动错误修正 JSON |
| 无法解析内部域名 | 缺少 DNS/hosts | 配置 DNS，或临时更新 A/Windows hosts |

## 11. 安全检查清单

- [ ] A、B 均为 ARM64，所有二进制和镜像架构一致。
- [ ] Windows 只能访问 A 的 `443`。
- [ ] B 的 `8443` 只允许 A 的 IP。
- [ ] Go `8080` 和 FastAPI `8000` 只监听回环。
- [ ] vLLM、Embedding、Milvus、IoTDB、openGauss、MQTT 不对用户网段开放。
- [ ] A、B 和 Windows 均正确信任内部 CA。
- [ ] 证书包含正确 SAN，未关闭 TLS 校验。
- [ ] 当前 B 未启用 API Key；若启用，A/B 值一致且未提交到 Git。
- [ ] A 的 `main-server.json` 和 B 的 `.env` 均为 root:root、`0600`。
- [ ] B 已关闭 `DEMO_SIMULATION`。
- [ ] `APP_ENV=production`，FastAPI `/docs` 已关闭。
- [ ] openGauss 已使用持久化会话，不依赖内存。
- [ ] MQTT 已启用认证、TLS 和 ACL。
- [ ] Nginx 两级均关闭 SSE 缓冲。
- [ ] Electron 未开启 `nodeIntegration`，未关闭 `webSecurity`。
- [ ] Electron 渲染进程不持有服务令牌和数据库凭据。
- [ ] `X-User-Id` 只有在主服务完成登录校验后才能作为可信身份使用。
- [ ] 已对 B 宕机、超时、证书失效、错误令牌和网络中断进行演练。
- [ ] 已记录所有发布制品 SHA-256 和 Git 提交号。
