# 设备预测性维护与智能助手需求文档

> 文档状态：需求修订稿<br>
> 更新日期：2026-11-26<br>
> 适用对象：业务方、产品、前端、后端、测试与系统集成人员

## 1. 文档目的与边界

本文定义设备预测性维护与智能助手两条业务线的目标、范围、功能要求、业务规则和验收标准。

用户端与 MES 主服务器之间的鉴权、通信协议、会话接入和接入页面由其他团队负责。本文只描述本项目的业务需求以及与主服务器之间的能力边界，不设计用户如何登录或如何与主服务器通信。

预测性维护以主服务器为中心：数采软件只向主服务器供数，主服务器通过 MQTT 向算力服同步指定数据，并定时调用算力服分析接口。算力服作为旁路分析服务，不参与主服务器的用户请求、图表查询、工单管理和审计处理。

技术实现、接口协议、RAG 服务组成、数据存储和部署方式见 [设计文档](./设计文档.md)。

### 1.1 当前实现状态

当前 Go `main_server` 已实现的能力仅包括：

- 进程健康检查和服务就绪检查。
- 主服务名称、版本、运行环境和当前时间查询。
- 请求 ID、访问日志、panic 恢复和统一 JSON 错误响应。
- 面向智能助手的聊天请求校验和 SSE 代理，聊天内容由算力服 FastAPI 生成。

设备预测性维护、MQTT 同步、主服务器数据库、自动建单、人工审核、历史查询和算力结果校验仍
属于后续规划，当前 Go 服务不实现这些业务，也不提供通用反向代理。

本版新增“每日 24 小时事件化分析”为目标需求：算力服按设备返回事件列表 `events[]`，一个
连续异常区间为一个事件。当前算力服仍按请求返回单设备分析结果，尚未实现事件化契约；联调前
以设计文档第 4.2 节为最终目标。

### 1.2 本期智能助手会话管理约定

本期前端和 Go 主服务仅新增智能助手会话管理接入，范围限定为会话列表、会话创建、会话详情、
重命名、删除、历史消息读取、历史消息分页以及继续已有会话。

- 本期不建设用户账号、登录、角色或权限体系。用户端与 MES 主服务器之间的鉴权仍按总体边界由
  其他团队负责，本项目当前 Go 服务不实现用户鉴权。
- 前端不使用 `client_id`，不发送 `X-Client-Id`；Go 主服务在助手聊天和会话管理请求中不向算力服
  传递 `X-User-Id` 或 `X-Client-Id`。
- 会话统一归属算力服的 `anonymous` 会话空间。切换工作站登录账号、重新登录、刷新页面或重新
  打开客户端均不改变会话归属，因此不会生成全新的对话历史。
- 同一算力服实例及其 openGauss 数据库下的会话历史为全局共享历史。若不同现场共用算力服但
  需要隔离历史，应通过独立实例或独立数据库隔离，不通过前端用户标识隔离。
- 会话、消息和引用持久化在 openGauss。算力服或 Go 服务进程重启后历史仍保留；仅当未配置
  openGauss、数据库被清空、连接到不同数据库或重新创建无持久化卷的容器时才会丢失。
- 消息反馈、工作流列表、报表列表、报表下载和浏览器会话认领不属于本期会话管理范围，保留为
  后续能力。

## 2. 项目目标

本项目面向核电站 MES 工作站，在现有监测总览能力之上新增两条业务线：

- **设备预测性维护**：由主服务器定时调用算力服分析近期设备数据及历史工单，自动形成风险结果和内部维护工单，给出可追溯的风险依据和维护建议。
- **智能助手**：基于固定、预先整理并版本化发布的站内知识库与只读业务数据，回答设备、运行和维护问题，并支持生成分析结果与报告。

项目应满足以下总体目标：

- 降低设备运行风险识别的遗漏率，并让结论可以追溯到具体数据和知识来源。
- 让用户能够通过自然语言查询制度、手册、历史案例和只读业务数据。
- 所有分析和建议仅用于辅助人工判断。系统可自动生成内部维护工单，但不自动执行设备操作、外部 MES 工单流转或报警确认。
- 算力服旁路故障、分析超时或 MQTT 同步异常不得影响主服务器处理鉴权、图表、工单和其他业务。
- 系统能够在国产算力服务器、隔离网络和固定知识库条件下稳定运行。

## 3. 角色与职责边界

| 角色 | 职责 |
| --- | --- |
| 业务用户 | 查看待确认的预测维护事件、综合判断、关键依据和建议，并使用智能助手 |
| 授权维护人员 | 核查预测维护事件，提交“准确”或“需修正”的人工审核结论并归档，按线下流程决定是否执行维护 |
| 运维发布人员 | 准备固定知识语料、构建版本化知识包并执行索引发布和回滚 |
| 主服务器团队 | 负责数采数据入库、关系数据库、MQTT 发布、定时调度、结果校验、建单、展示、历史查询接口和审计 |
| 数采团队 | 负责按约定协议和周期向主服务器提供设备采集数据 |
| 算力服开发与运维 | 负责 MQTT 数据接收、近期时序数据、维护分析编排、完整 RAG 服务、模型服务和算力服运行 |

本项目不负责：

- 监测总览、报警确认和其他既有 MES 页面的业务实现。
- 主 MES 的账号体系、组织权限、设备主数据、关系数据库、定时调度和工单页面建设。
- 用户端与主服务器之间的鉴权、通信协议、会话接入和页面交互设计。
- 知识文档的作者维护、审批、用户上传、删除和在线管理界面。
- 现场设备采集链路、设备控制、工单派发和自动维修执行。
- 算力服对主服务器数据库的直接访问、用户界面和工单状态管理。
- 模型分析结果的自动审批。

## 5. 功能需求

### 5.1 设备预测性维护

本期前端仅负责“设备预测性维护”模拟页。用户进入页面后直接查看待人工审核的事件列表，不建设全站健康概览、设备健康分类总览或全站数据完整性页面。页面使用“事件”“新事件分析”和“已确认记录”作为统一用户术语，后端内部维护工单仍作为业务对象管理。

预测维护采用每日固定批次分析上一自然日 24 小时数据。事件定义为同一设备上的一个连续异常
区间，由一个或多个规则依据组成；同一设备在一个 24 小时窗口内可以产生多个事件，分别展示、
分别审核、分别归档。

| 编号 | 需求 |
| --- | --- |
| FR-MA-01 | 用户进入设备预测性维护页面后直接查看待确认事件，并可按站点和设备类型进行结构化筛选；关键词搜索仅作为附加检索能力。 |
| FR-MA-02 | 事件使用单一 `healthLevel` 字段评价健康等级，支持 `insufficient_data`（数据不足）、`watch`（需关注）和 `inspect`（建议检修）三类，不设置 `normal` 状态。 |
| FR-MA-03 | 主服务器应每天在配置的固定时间、以独立后台任务对上一自然日（00:00–24:00，站点本地时区）逐站点、逐设备调用算力服维护分析接口；用户不直接发起分析，也不订阅分析任务进度。窗口结束后运行，避免窗口漂移和重复上报。 |
| FR-MA-04 | 数采软件只向主服务器供数；主服务器通过 MQTT 持续向算力服同步指定近期数据，并保存设备、事件、工单和已发布结果。 |
| FR-MA-05 | 算力服应使用 MQTT 同步的近期数据，并通过主服务器查询接口获取去标识化历史工单、已发布 AI 结果和人工审核结论。 |
| FR-MA-06 | 数据不足时必须返回 `insufficient_data`，不得用模型推测补齐缺失数据。 |
| FR-MA-07 | 主服务器应校验算力服返回的结构化结果，并按事件逐条创建或更新内部检修工单；`watch`、`inspect` 事件自动生成内部检修工单。`insufficient_data` 作为独立的数据质量事件展示并支持人工核查，但不生成检修工单。 |
| FR-MA-08 | 用户应能查看事件的风险等级、规则依据、模型解释、最多 3 条建议动作和按条件显示的数据限制；设备类型为探测器和备电。AI 综合分析区域统一为“综合判断、关键依据、建议动作、条件数据限制”四部分，不再分别展示“支持证据、数据缺口、后续复核、维护建议”四个独立卡片。授权维护人员提交一次人工审核结论（`accurate` 准确或 `needs_revision` 需修正）并归档。审核结论、说明和时间是唯一人工判断记录；审核人身份仅在主服务器审计中保存，算力服副本按脱敏约定不保存身份。列表中的 AI 评价标签由审核结论派生，不单独提交或保存 AI 评价。同一设备的不同事件分别展示、分别提交审核。 |
| FR-MA-09 | 算力服应执行数据质量、阈值、趋势、相关性和历史上下文规则，按设备输出事件列表 `events[]`；每个事件至少包含 `event_id`、`equipment_id`、`event_type`、`event_code`、`severity`、`start`、`end`、`findings`、`actions` 和 `limitations`。风险等级和关键依据由确定性规则确定，不由模型自由判断。 |
| FR-MA-10 | 模型只根据压缩后的规则事实为每个事件生成一段 `explanation`，不得修改风险等级、增加规则中不存在的数值、生成数据缺口或自行选择维护动作。模型输出必须经过结构校验，校验失败时该事件使用规则模板解释。 |
| FR-MA-11 | 建议动作应由版本化动作库按事件内规则代码映射生成，每个事件最多返回 3 条并按主建议、次建议排序。“后续复核”作为普通建议动作处理，不设置独立字段或独立界面区域。 |
| FR-MA-12 | 数据质量按事件区间和设备窗口分别评估：单个事件区间内关键指标无数据或完整率低于配置门限时，该事件返回 `insufficient_data`，且不调用解释模型、不生成由维护规则或动作库派生的普通维护建议；界面只展示无法判断的原因、缺失数据和补数条件。24 小时窗口内局部缺数不得阻断其他区间的事件。只有整窗关键指标完全不可用时，才生成设备级数据质量事件。若事件已由既有设备告警或其他权威业务事件触发，允许在综合判断中保留告警状态保持和现场核查提示，但不扩展为新的建议动作。辅助指标缺失仅生成数据限制，不阻止其他规则继续分析。 |
| FR-MA-13 | 分析结果必须记录规则集、动作库、Prompt 和模型版本，以及解释来源（模型或模板），以支持结果追溯和规则回滚。 |
| FR-MA-14 | 不设置独立的 `analysisStatus` 字段。事件级 `healthLevel` 按该事件区间和依据聚合：关键指标无有效数据或完整率低于门限时为 `insufficient_data`；否则按 `inspect` 优先于 `watch` 聚合。设备级结果按 `insufficient_data` > `inspect` > `watch` 的优先级取最高；没有事件时为内部 `normal`，不生成事件。前端按下表直接映射：`insufficient_data`→数据不足，`watch`→需关注，`inspect`→建议检修。同一设备的不同事件分别展示、分别审核。 |
| FR-MA-15 | 同一设备在一个 24 小时窗口内的一个连续异常区间构成一个事件。时间重叠或间隔不超过配置合并阈值的多个规则命中合并为同一事件，事件内保留多条依据；不重叠的异常区间分别构成不同事件。仅用于上下文的规则（如历史重复）不单独成事件。 |
| FR-MA-16 | 同一设备同一分析窗口可产生多个事件。算力服必须在配置的事件数上限内返回窗口内全部事件，不得因展示上限丢弃事件；每个事件独立生成依据、动作、解释、数据质量和区间数据，并按 `start` 排序。超过安全上限时合并相邻低等级事件并记录日志，不得静默丢弃。 |
| FR-MA-17 | 每个事件返回异常区间、设备级 24 小时上下文曲线、事件区间曲线、上月同期和去年同期对比。曲线使用聚合桶返回；历史时段无数据时标记 `available=false` 并说明原因，不得按 0 处理。24 小时上下文每个设备只返回一份，事件内通过区间标识关联。 |
| FR-MA-18 | `event_id` 由站点、设备、主规则代码和事件开始时间（epoch 毫秒）确定，重复分析必须产生相同标识。同一持续事件跨批次按 `event_id` 更新，不重复建单；不同事件不得被抑制窗口合并。窗口结束时仍异常的事件标记 `open_at_end=true`，下一批次继续合并；窗口开始时已异常的事件标记 `open_at_start=true`，主服务器应沿用该设备同类型未关闭事件的 `event_id`，避免被窗口起点截断后重复建单。 |
| FR-MA-19 | 每个事件单独调用解释模型生成 `explanation`，并在该事件的候选动作中选择一个主建议；模型失败时该事件使用模板解释。动作库按事件内依据映射，去重后最多 3 条。 |
| FR-MA-20 | 主服务器应在每天固定时间先调用算力服 prepare 接口，对上一自然日全部站点、全部设备启动后台预分析批次；算力服异步完成规则、事件、区间、设备级 24 小时上下文、事件曲线和解释，并写入批次缓存。主服务器轮询批次状态，就绪后逐设备调用分析接口；窗口、`data_cutoff`、`mqtt_watermark` 和规则/动作/提示词版本一致时直接返回缓存事件。 |
| FR-MA-21 | 每个事件对应一份人工审核与归档记录。主服务器在事件创建、更新时通过工单副本接口同步事件和 AI 结果；在审核提交和审核修改时通过专用接口 `PUT /internal/v1/maintenance/work-orders/{event_id}/review` 同步到算力服 openGauss。算力服只保留最新一份，修改时覆盖，不保留历史版本。字段沿用当前审核表单：`outcome`、`comment`、`reviewed_at`、`updated_at`、`archived_at`；审核人身份不进入副本。主服务器仍是权威来源。 |
| FR-MA-22 | 预分析缓存必须记录批次、窗口、`data_cutoff`、`mqtt_watermark`、规则集/动作库/Prompt 版本和数据截止时间。请求窗口、水位或版本与缓存不一致时，不得返回旧缓存；应重新分析或在有限时间内等待新批次。缓存非权威结果，主服务器建单前必须校验。 |

预测性维护页面还应满足以下交互规则：

- 页面整体结构以当前实现为基准：事件列表、筛选、分页、右侧人工审核栏和响应式布局保持现状；详情弹窗设计宽度为 1080px，最大宽度不超过视口，最大高度不超过 920px 与“视口高度减 40px”中的较小值。
- 事件列表一行一个事件，同一设备可以在列表中出现多行；每行展示站点、设备、事件类型、异常区间、健康等级和审核状态。
- 事件详情按单个事件展示：设备级 24 小时上下文曲线、高亮本次异常区间、事件区间曲线，以及上月同期/去年同期切换；历史时段无数据时显示“无历史数据”，不按 0 处理。
- 同一设备的不同事件分别提交人工审核、分别归档。
- 探测器事件只展示电离室剂量率和雨量数据；备电事件只展示当前电量、参考续航和历史参考，两类事件不得在详情中同时展示两类数据。
- AI 综合分析区域顶部保留模型名称和生成时间；主体依次展示综合判断、最多 3 条关键依据、最多 3 条建议动作，并在存在数据问题时于底部显示一条数据限制提示。
- AI 综合分析区域不新增抽屉、Tab、折叠区或页面级操作栏，不将置信度或模型精度作为页面展示内容。
- 人工审核结论 `accurate` 表示确认 AI 结论准确，`needs_revision` 表示 AI 结论需修正；两者均进入已确认归档记录并保持 `confirmed` 状态。
- AI 评价标签只是人工审核结论的展示形式，不再单独维护评价等级、评价说明或评价时间。
- 页面不使用“工单管理”“待确认工单”等用户术语。业务内容统一使用“事件”“待确认事件”和“新事件分析”；已归档页签使用“已确认记录”，对应列表标题使用“已确认事件记录”。

自动建单还应满足以下规则：

- 事件按 `event_id` 幂等：同一持续事件跨批次只保留一张工单并更新最新综合判断、关键依据、建议动作和数据限制，不重复推送新工单。
- 不同异常区间即使属于同一设备、同一风险类型，也分别创建工单；抑制窗口只用于重复通知，不得把不同事件合并成一张工单。
- 窗口结束时仍异常的事件在下一批次按 `event_id` 续接，不重复建单。
- 人工审核提交或修改后，主服务器更新权威记录，并通过 `PUT /internal/v1/maintenance/work-orders/{event_id}/review` 同步算力服副本；副本只保留最新审核，不保留修改历史。
- 审核副本接口要求事件已存在于算力服工单副本中：不存在返回 `404`；`updated_at` 早于副本当前版本返回 `409`；成功后 `status=confirmed`，并写入 `archived_at`。
- 算力服规则分析超时、不可用或返回无效结构化结果时，本轮只记录运维告警和调用日志，不生成异常工单。
- 规则分析成功后，仅解释模型超时或输出无效时，算力服使用规则模板生成解释并继续返回分析结果，不因解释模型故障丢弃有效规则结论。
- 主服务器保存工单、已发布 AI 结果和单一人工审核记录，用户界面只从主服务器读取。

## 6. 业务规则

- 主服务器权威：采集数据、事件、工单、已发布结果、人工审核和审计以主服务器关系数据库为准；算力服只保存工单/审核副本和短期预分析缓存，不作为权威来源。
- 单向供数：数采软件只连接主服务器；算力服仅通过主服务器发布到 MQTT 的指定数据和受控历史查询接口获取分析所需信息。
- 旁路隔离：算力服分析不得占用主服务器用户请求线程，不得直接连接主服务器数据库，也不得反过来控制工单状态。
- 预分析缓存：算力服可提前计算并缓存上一自然日的事件，用于降低主服务器调用延迟；缓存不得替代主服务器校验、建单、发布和审核。
- 审核副本：算力服 openGauss 保存每个事件的最新人工审核与归档副本；主服务器保存权威记录和审计，副本不保存历史版本和审核人身份。
- 自动内部建单：主服务器根据算力服返回的事件列表按 `event_id` 自动创建或更新内部维护工单，但不触发外部 MES 工单、设备控制或报警确认。
- 规则执行位置：预测维护规则引擎位于算力服，负责数据质量、阈值、趋势、相关性和历史上下文判断；主服务器负责调度、结果校验、事件去重、工单和人工审核，不重复执行预测规则。
- 事件化：同一设备上一个连续异常区间构成一个事件；时间重叠或间隔不超过合并阈值的多个规则依据合并为同一事件，不重叠的区间分别成事件。
- 事件幂等：`event_id` 由站点、设备、主规则代码和事件开始时间（epoch 毫秒）确定；同一持续事件跨批次更新，不同事件不得被抑制窗口合并。
- 事件数据：每个事件返回异常区间、设备级 24 小时上下文、事件区间曲线和上月/去年同期；缺失历史标记不可用，不按 0 处理。
- 确定性规则优先：风险等级、关键依据、数据限制和建议动作代码由可测试的规则与动作库完成；模型只负责根据既有事实为每个事件生成简短解释。
- 证据优先：事实性回答必须基于设备数据或知识库引用，不得凭模型常识补造站内事实。
- 数据不足不猜测：缺少关键数据时输出明确的数据限制或 `insufficient_data`，不得由模型补齐。
- 解释降级：解释模型失败不得丢弃有效规则结果；模板解释与模型解释使用同一展示结构，并通过 `explanation_source` 区分。
- 动作确定性：模型不得自行选择或改写维护动作，建议动作只来自版本化动作库。
- 人工最终审核：维护建议、报告结论和模型分析结果仅供人工核查，授权维护人员提交的人工审核结论是最终人工判断记录。
- 只读工具：智能助手只拥有业务数据读取能力，不拥有设备控制、报警确认或工单写入能力。
- 审核边界：人工审核结论仅作为单一事实来源用于本次分析上下文和统计，不作为在线训练数据；回查结果必须去标识化。
- 固定知识：知识文档不通过用户端或主服务器上传，不接受运行时在线修改。
- 版本一致：一次查询只使用一个知识索引版本，引用的文档版本必须与本次查询版本一致。

## 7. 非功能需求

### 7.1 安全与合规

- 用户鉴权和权限判断由主服务器负责，算力服只接受受信任的主服务器分析调用。
- 本期智能助手会话管理可在无用户鉴权条件下运行。全局会话空间中的历史可供同一算力服实例下的
  所有接入用户查看，因此访问控制依赖固定工作站和受控网络边界。
- 算力服内部模型、embedding、rerank 和向量数据库不得直接暴露给用户端。
- 分析请求和结果使用 HTTPS；MQTT 使用受控凭据，生产环境启用 TLS 和主题级 ACL。
- 算力服只能通过主服务器历史查询接口读取去标识化历史工单、已发布 AI 结果和人工审核结论，不能直接访问主服务器数据库。
- 主服务器调用算力服必须设置连接超时、读取超时、并发上限和熔断，不得因算力服异常阻塞其他任务。
- 知识语料和业务数据按来源、密级和权限范围控制引用。

### 7.2 可用性与可靠性

- 单次模型故障或 RAG 依赖故障不得导致整站服务不可用；预测维护解释模型故障时应使用模板解释，保留有效规则结论。
- 算力服宕机、分析超时、结果格式错误或 MQTT 中断不得影响主服务器鉴权、图表、工单、其他定时任务和用户请求。
- MQTT 发布应采用独立后台任务和事务性待发送记录；消息积压不得阻塞主数据库事务。
- 分析调用和 MQTT 消费应使用幂等键、有限重试和熔断，禁止失败后在同一周期形成重试风暴。
- 数据读取、模型调用、向量检索和 rerank 应设置超时、有限重试和并发控制。
- MQTT 消息、分析请求和工单创建应支持幂等，避免重复消息、重复调用和重复工单。

### 7.3 性能与容量

首版在以下硬件基线上运行：

- 鲲鹏 920-Smart，32 核。
- 128 GB DDR4 2933。
- 4 TB M.2。
- 昇腾 Atlas 300I A2 64 GB × 1。
- 1250 W ATX 电源。
- Qwen3-30B-A3B，首版按 W8A8 量化版本验证。

预测维护解释层允许使用 Qwen3-14B 或经过压测的等价模型；Qwen3-30B-A3B 仍是目标模型和智能助手主模型。具体上下文长度、并发数、首 token 延迟和 token/s 目标由业务方确认，并通过实机压测固化。单卡容量不足以支持 30B 模型 BF16 生产部署。

主服务器与算力服应使用独立主机资源。算力服旁路压测时，主服务器的用户请求、图表查询、工单处理和既有定时任务仍需满足各自的基线指标。

- 预测维护事件曲线按聚合桶返回：24 小时上下文的桶粒度不小于 5 分钟，单指标单时段点数不超过配置上限；事件区间可使用更高精度。
- 每设备每日事件数、每事件依据数、动作数和曲线点数均应设置上限；超限时合并相邻低等级事件或记录截断日志，不得静默丢弃。
- 上月同期和去年同期查询至少覆盖 13 个月历史；保留期不足时返回明确不可用标记，不得用 0 或空数组冒充历史数据。
- 预分析批次应在主服务器调用前完成；批次耗时、并发数、缓存命中率和逐设备失败率应可观测。
- 预分析缓存应设置 TTL 和容量上限；缓存未命中时主服务器可选择等待有限时间或回退同步分析，不得无限等待。
- 人工审核副本的同步应在有限时间内完成；主服务器同步失败时应重试，不得让 openGauss 副本长期停留在旧审核。

### 7.4 离线和国产化

- 系统应支持隔离网络部署，不依赖公网服务。
- 镜像、模型、embedding 模型、rerank 模型、知识语料和依赖应支持离线导入与版本校验。
- 关系库、向量库、对象存储和应用运行时应在 ARM64 环境完成兼容性验证。
- Go 主服务应使用运行时可修改的配置文件保存监听地址、算力服地址、聊天路径和超时；不得
  将具体用户的 IP、域名或端口编译进二进制。
- 更换用户现场时，同一 ARM64 Go 二进制应通过修改配置文件适配不同 A/B 机器；配置变化后
  允许通过重启服务生效，不要求重新构建。
- 配置文件缺失、格式错误或包含未知字段时，服务应拒绝启动并输出明确错误。

### 7.5 可维护性与可观测性

- RAG 知识包应支持版本发布、校验、回滚和问题定位。
- 运维应能查看模型、embedding、rerank、向量库和索引版本的可用性。
- 应记录 MQTT 发布与消费延迟、积压、幂等命中、水位等待、历史查询、规则集版本、动作库版本、规则命中、模型解释、模板回退、结果校验和建单等关键阶段的耗时与错误。
- Go 主服务配置应作为独立部署资产备份，日志和错误信息不得输出 API Key。
- 更换算力服地址或聊天路径后，应通过健康检查和实际 SSE 请求确认配置生效。

## 8. 验收标准

### 8.1 预测性维护

- 预测维护页直接进入待确认事件列表，不展示全站健康概览，并支持按站点和设备类型进行结构化组合筛选。
- 事件风险状态能按“数据不足、需关注、建议检修”三类正确展示，不出现正常状态。
- 主服务器能每天在固定时间对上一自然日的探测器和备电逐设备分析，并使用 MQTT 同步的近期数据输出风险等级、关键依据、建议动作和条件数据限制。
- 数据不足、设备不存在和权限不足时返回明确结果。
- `watch`、`inspect` 事件能自动生成内部检修工单；`insufficient_data` 作为独立的数据质量事件展示，但不生成检修工单。
- 同一持续事件按 `event_id` 跨批次更新，不重复建单；不同异常区间即使属于同一设备、同一风险类型，也分别生成事件和工单，抑制窗口不合并不同事件。
- 同一设备窗口内两个不重叠异常区间返回两个事件，事件按各自的 `start` 排序。
- 同一事故的多个规则依据（如市电中断、续航下降、电压低）按时间簇合并为一个事件；时间重叠的依据不拆成多个事件。
- 每个事件返回异常区间、设备级 24 小时上下文、事件区间曲线、上月同期和去年同期；缺失历史返回不可用标记，不按 0 处理。
- 跨午夜仍异常的事件在下一批次按 `event_id` 续接，不重复建单。
- 24 小时窗口局部缺数不阻断其他区间的事件；整窗无数据时生成独立的数据质量事件。
- 主服务器先调用 prepare 启动全量预分析，批次就绪后逐设备调用分析接口命中缓存；窗口、水位或规则/动作/提示词版本不一致时不返回旧缓存。
- 缓存未就绪、算力服重启或缓存丢失时，主服务器能回退同步分析或重新 prepare，不产生重复事件或工单。
- 每个事件的审核提交和修改由主服务器通过 `PUT /internal/v1/maintenance/work-orders/{event_id}/review` 同步到算力服 openGauss 副本；副本只保留最新一份，修改后覆盖，不保留历史。
- 审核副本接口对未知事件返回 `404`，对早于副本版本的 `updated_at` 返回 `409`；成功后 `status=confirmed`，`archived_at` 在首次归档时写入，后续修改保留原归档时间。
- 算力服宕机、超时、返回无效 JSON 或 MQTT 中断时，主服务器其他业务正常，且不生成异常工单。
- 解释模型超时或返回无效内容时，只要规则分析结果有效，系统仍通过模板解释发布事件，并记录 `explanation_source=template`。
- 用户能对事件提交一次“准确”或“需修正”的人工审核结论并归档；归档后事件进入已确认记录，AI 评价标签由审核结论派生。
- 归档后允许修改审核意见；修改覆盖同一份审核记录，更新 `updated_at`，不新增历史记录。
- 人工审核只产生一份审核记录，不再生成相互独立的工单确认记录和 AI 评价记录。
- 事件详情采用当前 1080px 设计宽度，右侧审核栏和响应式行为与现有实现一致；数据区按事件设备类型只展示对应面板，AI 综合分析区域保持综合判断、关键依据、建议动作和条件数据限制。
- AI 区域最多展示 3 条关键依据和 3 条建议动作，不展示旧的支持证据、数据缺口、后续复核、维护建议四个独立卡片，也不展示置信度或模型精度。
- `insufficient_data` 事件不调用解释模型，不展示由维护规则或动作库派生的普通维护建议，只展示数据不足原因、缺失项和补数条件；既有设备告警事件可保留告警状态保持和现场核查提示，但不得新增独立建议动作。
- 预测维护页面统一使用“事件”“新事件分析”和“已确认记录”等术语；已确认记录列表标题使用“已确认事件记录”。
- 自动分析结果不能触发任何设备操作、报警确认或外部 MES 工单流转。

### 8.2 智能助手与 RAG

- 助手能区分知识问答、设备状态查询和报告请求。
- 事实性回答经过召回和 rerank，并包含可定位引用。
- 知识无命中时明确返回无依据结果，不编造引用。
- 固定知识包可以离线构建、校验、原子切换和回滚。
- 单次查询不会混用新旧知识版本。
- embedding、rerank 或向量库不可用时返回明确错误或已批准的降级结果。
- 用户能够查看、打开、重命名、删除并继续已有会话，刷新页面后会话和历史消息仍可恢复。
- 用户能够按时间向前分页加载历史消息，翻页结果不重复、不丢失。
- 切换 MES 管理员账号、重新登录或重新打开客户端后，仍看到同一算力服实例的同一份会话历史。
- Go 主服务对助手聊天和会话管理请求不传递用户或浏览器身份，算力服统一使用 `anonymous` 会话空间。
- 会话和消息写入 openGauss 后，算力服或 Go 主服务进程重启不导致历史丢失。
- 本期前端不提供消息反馈、工作流列表、报表列表、报表下载和浏览器会话认领入口。

### 8.3 安全与可运维性

- 用户端无法直接访问算力服内部模型、embedding、rerank 或向量库。
- 无有效服务令牌或来源非法的请求被拒绝并记录审计。
- 算力服无法直接访问主服务器数据库，历史查询接口只返回去标识化数据。
- MQTT 重复、乱序和积压不会产生重复记录，也不会让算力服使用未达到请求水位的数据生成正式结论。
- 算力服旁路故障或高负载不会阻塞主服务器鉴权、图表、工单和其他定时任务。
- 用户端和主服务器接口中不存在知识文档上传、删除、审核或索引管理入口。
- 系统能够在隔离网络完成启动、知识发布、健康检查和故障恢复。
- Go 主服务能够从 JSON 配置启动，并在缺失、格式错误、未知字段、非法 URL、非法路径或非法
  超时时拒绝启动。
- 修改 `compute.base_url`、`compute.chat_path` 或 `compute.assistant_path` 后，无需重新编译
  即可将同一 Go 二进制用于不同 A/B 机器，并成功代理聊天 SSE 和会话管理请求。

## 9. 依赖与待确认事项

| 类别 | 待确认内容 | 影响 |
| --- | --- | --- |
| 外部接口 | 主服务器分析调用接口、历史查询接口、MQTT 主题与消息契约、服务令牌轮换 | 决定联调时间与数据可用性 |
| 硬件 | CANN、NPU 驱动、鲲鹏平台版本和磁盘冗余方案 | 决定镜像、设备挂载和可靠性 |
| 模型容量 | 30B 目标模型及 14B 解释模型在单卡下的上下文、并发、延迟和吞吐 | 决定预测维护解释模型选择及是否需要增加推理卡 |
| 知识范围 | 固定语料范围、版本频率、密级和权限规则 | 决定知识包和检索过滤条件 |
| RAG 部署 | embedding/rerank 使用 CPU 还是 NPU | 决定内存/显存配额和检索延迟 |
| 数据库 | 主服务器关系库、算力服时序库、向量库和对象存储的具体产品与版本 | 决定兼容性、备份和索引发布方案 |
| 数据规则 | 数采频率、MQTT 同步时效、异常阈值、规则集、动作库、事件合并阈值、事件数上限、抑制窗口和历史窗口 | 决定维护分析的准确性、时效和可维护性 |
| 事件化 | 事件合并阈值、`event_id` 规则、跨午夜续接、数据质量事件是否进入列表 | 决定事件数量、去重和审核粒度 |
| 同期数据 | 上月/去年同期定义（日历月平移或固定天数）、站点时区和历史保留期 | 决定同比数据是否可用 |
| 预分析 | prepare 触发时间、数据稳定窗口、批次并发、缓存 TTL/容量、缓存未命中回退策略 | 决定主服务器调用延迟和一致性 |
| 审核副本 | 接口路径、404/409 语义、审核字段、归档时间、修改覆盖策略、审核人是否进入副本 | 决定 openGauss 副本与主服务器的一致性 |
| 报表 | 报告格式、模板、存储期限和下载权限 | 决定报告生成和存储方案 |
