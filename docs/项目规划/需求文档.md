# 设备预测性维护与智能助手需求文档

> 文档状态：需求修订稿<br>
> 更新日期：2026-11-13<br>
> 适用对象：业务方、产品、前端、后端、测试与系统集成人员

## 1. 文档目的与边界

本文定义设备预测性维护与智能助手两条业务线的目标、范围、功能要求、业务规则和验收标准。

用户端与 MES 主服务器之间的鉴权、通信协议、会话接入和接入页面由其他团队负责。本文只描述本项目的业务需求以及与主服务器之间的能力边界，不设计用户如何登录或如何与主服务器通信。

预测性维护以主服务器为中心：数采软件只向主服务器供数，主服务器通过 MQTT 向算力服同步指定数据，并定时调用算力服分析接口。算力服作为旁路分析服务，不参与主服务器的用户请求、图表查询、工单管理和审计处理。

技术实现、接口协议、RAG 服务组成、数据存储和部署方式见 [设计文档](./设计文档.md)。

## 2. 项目目标

本项目面向核电站 MES 工作站，在现有监测总览能力之上新增两条业务线：

- **设备预测性维护**：由主服务器定时调用算力服分析近期设备数据及历史工单，自动形成风险结果和内部维护工单，给出可追溯的风险依据和维护建议。
- **智能助手**：基于固定、预先整理并版本化发布的站内知识库与只读业务数据，回答设备、运行和维护问题，并支持生成分析结果与报告。

项目应满足以下总体目标：

- 降低设备运行风险识别的遗漏率，并让结论可以追溯到具体数据和知识来源。
- 让用户能够通过自然语言查询制度、手册、历史案例和只读业务数据。
- 所有分析和建议仅用于辅助人工判断。系统可自动生成内部维护工单，但不自动执行设备操作、外部 MES 工单流转或报警确认。
- 算力服旁路故障、分析超时或 MQTT 同步异常不得影响主服务器处理鉴权、图表、工单和其他业务。
- 系统能够在国产算力服务器、隔离网络和固定知识库条件下稳定运行。

## 3. 角色与职责边界

| 角色 | 职责 |
| --- | --- |
| 业务用户 | 查看待确认的预测维护事件、综合判断、关键依据和建议，并使用智能助手 |
| 授权维护人员 | 核查预测维护事件，提交“准确”或“需修正”的人工审核结论并归档，按线下流程决定是否执行维护 |
| 运维发布人员 | 准备固定知识语料、构建版本化知识包并执行索引发布和回滚 |
| 主服务器团队 | 负责数采数据入库、关系数据库、MQTT 发布、定时调度、结果校验、建单、展示、历史查询接口和审计 |
| 数采团队 | 负责按约定协议和周期向主服务器提供设备采集数据 |
| 算力服开发与运维 | 负责 MQTT 数据接收、近期时序数据、维护分析编排、完整 RAG 服务、模型服务和算力服运行 |

本项目不负责：

- 监测总览、报警确认和其他既有 MES 页面的业务实现。
- 主 MES 的账号体系、组织权限、设备主数据、关系数据库、定时调度和工单页面建设。
- 用户端与主服务器之间的鉴权、通信协议、会话接入和页面交互设计。
- 知识文档的作者维护、审批、用户上传、删除和在线管理界面。
- 现场设备采集链路、设备控制、工单派发和自动维修执行。
- 算力服对主服务器数据库的直接访问、用户界面和工单状态管理。
- 模型分析结果的自动审批。

## 5. 功能需求

### 5.1 设备预测性维护

本期前端仅负责“设备预测性维护”模拟页。用户进入页面后直接查看待人工审核的事件列表，不建设全站健康概览、设备健康分类总览或全站数据完整性页面。页面使用“事件”“新事件分析”和“已确认记录”作为统一用户术语，后端内部维护工单仍作为业务对象管理。

| 编号 | 需求 |
| --- | --- |
| FR-MA-01 | 用户进入设备预测性维护页面后直接查看待确认事件，并可按站点和设备类型进行结构化筛选；关键词搜索仅作为附加检索能力。 |
| FR-MA-02 | 事件风险状态支持 `insufficient_data`（数据不足）、`watch`（需关注）和 `inspect`（建议检修）三类，不设置 `normal` 状态。 |
| FR-MA-03 | 主服务器应按配置周期在独立后台任务中调用算力服维护分析接口；用户不直接发起分析，也不订阅分析任务进度。 |
| FR-MA-04 | 数采软件只向主服务器供数；主服务器通过 MQTT 持续向算力服同步指定近期数据，并保存设备、工单和已发布结果。 |
| FR-MA-05 | 算力服应使用 MQTT 同步的近期数据，并通过主服务器查询接口获取去标识化历史工单、已发布 AI 结果和人工审核结论。 |
| FR-MA-06 | 数据不足时必须返回 `insufficient_data`，不得用模型推测补齐缺失数据。 |
| FR-MA-07 | 主服务器应校验算力服返回的结构化结果；`watch`、`inspect` 自动生成内部工单，`insufficient_data` 不生成异常工单。 |
| FR-MA-08 | 用户应能查看事件的风险等级、规则依据、模型解释、最多 3 条建议动作和按条件显示的数据限制；设备类型为探测器和备电。AI 综合分析区域统一为“综合判断、关键依据、建议动作、条件数据限制”四部分，不再分别展示“支持证据、数据缺口、后续复核、维护建议”四个独立卡片。授权维护人员提交一次人工审核结论（`accurate` 准确或 `needs_revision` 需修正）并归档。审核结论、说明、时间和审核人是唯一人工判断记录，列表中的 AI 评价标签由审核结论派生，不单独提交或保存 AI 评价。 |
| FR-MA-09 | 算力服应执行数据质量、阈值、趋势、相关性和历史上下文规则，输出 `health_level`、`findings`、`actions` 和 `limitations`。风险等级和关键依据由确定性规则确定，不由模型自由判断。 |
| FR-MA-10 | 模型只根据压缩后的规则事实生成一段 `explanation`，不得修改风险等级、增加规则中不存在的数值、生成数据缺口或自行选择维护动作。模型输出必须经过结构校验，校验失败时使用规则模板解释。 |
| FR-MA-11 | 建议动作应由版本化动作库按规则代码映射生成，最多返回 3 条并按主建议、次建议排序。“后续复核”作为普通建议动作处理，不设置独立字段或独立界面区域。 |
| FR-MA-12 | 关键指标无数据或数据完整率低于配置门限时必须返回 `insufficient_data`，且不调用解释模型、不生成由维护规则或动作库派生的普通维护建议；界面只展示无法判断的原因、缺失数据和补数条件。若事件已由既有设备告警或其他权威业务事件触发，允许在综合判断中保留与该既有事件相关的告警状态保持和现场核查提示，作为事件处置说明，不扩展为新的维护建议动作。辅助指标缺失仅生成数据限制，不阻止其他规则继续分析。 |
| FR-MA-13 | 分析结果必须记录规则集、动作库、Prompt 和模型版本，以及解释来源（模型或模板），以支持结果追溯和规则回滚。 |

预测性维护页面还应满足以下交互规则：

- 页面整体结构以当前实现为基准：事件列表、筛选、分页、运行数据面板、右侧人工审核栏和响应式布局保持现状；详情弹窗设计宽度为 1080px，最大宽度不超过视口，最大高度不超过 920px 与“视口高度减 40px”中的较小值。
- 探测器事件详情展示电离室剂量率和雨量数据；备电事件详情展示当前电量、参考续航和历史参考。
- AI 综合分析区域顶部保留模型名称和生成时间；主体依次展示综合判断、最多 3 条关键依据、最多 3 条建议动作，并在存在数据问题时于底部显示一条数据限制提示。
- AI 综合分析区域不新增抽屉、Tab、折叠区或页面级操作栏，不将置信度或模型精度作为页面展示内容。
- 人工审核结论 `accurate` 表示确认 AI 结论准确，`needs_revision` 表示 AI 结论需修正；两者均进入已确认归档记录并保持 `confirmed` 状态。
- AI 评价标签只是人工审核结论的展示形式，不再单独维护评价等级、评价说明或评价时间。
- 页面不使用“工单管理”“待确认工单”等用户术语。业务内容统一使用“事件”“待确认事件”和“新事件分析”；已归档页签使用“已确认记录”，对应列表标题使用“已确认事件记录”。

自动建单还应满足以下规则：

- 同一设备、同一风险类型在默认 24 小时、可配置的抑制窗口内只保留一张工单。
- 抑制窗口内再次命中相同风险时，更新已有工单的最新综合判断、关键依据、建议动作和数据限制，不重复推送新工单。
- 算力服规则分析超时、不可用或返回无效结构化结果时，本轮只记录运维告警和调用日志，不生成异常工单。
- 规则分析成功后，仅解释模型超时或输出无效时，算力服使用规则模板生成解释并继续返回分析结果，不因解释模型故障丢弃有效规则结论。
- 主服务器保存工单、已发布 AI 结果和单一人工审核记录，用户界面只从主服务器读取。

## 6. 业务规则

- 主服务器权威：采集数据、工单、已发布结果、人工结论和审计以主服务器关系数据库为准，算力服不保存工单或已发布结果。
- 单向供数：数采软件只连接主服务器；算力服仅通过主服务器发布到 MQTT 的指定数据和受控历史查询接口获取分析所需信息。
- 旁路隔离：算力服分析不得占用主服务器用户请求线程，不得直接连接主服务器数据库，也不得反过来控制工单状态。
- 自动内部建单：主服务器根据算力服返回的结构化字段自动创建内部维护工单，但不触发外部 MES 工单、设备控制或报警确认。
- 规则执行位置：预测维护规则引擎位于算力服，负责数据质量、阈值、趋势、相关性和历史上下文判断；主服务器负责调度、结果校验、抑制窗口、工单和人工审核，不重复执行预测规则。
- 确定性规则优先：风险等级、关键依据、数据限制和建议动作代码由可测试的规则与动作库完成；模型只负责根据既有事实生成简短解释。
- 证据优先：事实性回答必须基于设备数据或知识库引用，不得凭模型常识补造站内事实。
- 数据不足不猜测：缺少关键数据时输出明确的数据限制或 `insufficient_data`，不得由模型补齐。
- 解释降级：解释模型失败不得丢弃有效规则结果；模板解释与模型解释使用同一展示结构，并通过 `explanation_source` 区分。
- 动作确定性：模型不得自行选择或改写维护动作，建议动作只来自版本化动作库。
- 人工最终审核：维护建议、报告结论和模型分析结果仅供人工核查，授权维护人员提交的人工审核结论是最终人工判断记录。
- 只读工具：智能助手只拥有业务数据读取能力，不拥有设备控制、报警确认或工单写入能力。
- 审核边界：人工审核结论仅作为单一事实来源用于本次分析上下文和统计，不作为在线训练数据；回查结果必须去标识化。
- 固定知识：知识文档不通过用户端或主服务器上传，不接受运行时在线修改。
- 版本一致：一次查询只使用一个知识索引版本，引用的文档版本必须与本次查询版本一致。

## 7. 非功能需求

### 7.1 安全与合规

- 用户鉴权和权限判断由主服务器负责，算力服只接受受信任的主服务器分析调用。
- 算力服内部模型、embedding、rerank 和向量数据库不得直接暴露给用户端。
- 分析请求和结果使用 HTTPS；MQTT 使用受控凭据，生产环境启用 TLS 和主题级 ACL。
- 算力服只能通过主服务器历史查询接口读取去标识化历史工单、已发布 AI 结果和人工审核结论，不能直接访问主服务器数据库。
- 主服务器调用算力服必须设置连接超时、读取超时、并发上限和熔断，不得因算力服异常阻塞其他任务。
- 知识语料和业务数据按来源、密级和权限范围控制引用。

### 7.2 可用性与可靠性

- 单次模型故障或 RAG 依赖故障不得导致整站服务不可用；预测维护解释模型故障时应使用模板解释，保留有效规则结论。
- 算力服宕机、分析超时、结果格式错误或 MQTT 中断不得影响主服务器鉴权、图表、工单、其他定时任务和用户请求。
- MQTT 发布应采用独立后台任务和事务性待发送记录；消息积压不得阻塞主数据库事务。
- 分析调用和 MQTT 消费应使用幂等键、有限重试和熔断，禁止失败后在同一周期形成重试风暴。
- 数据读取、模型调用、向量检索和 rerank 应设置超时、有限重试和并发控制。
- MQTT 消息、分析请求和工单创建应支持幂等，避免重复消息、重复调用和重复工单。

### 7.3 性能与容量

首版在以下硬件基线上运行：

- 鲲鹏 920-Smart，32 核。
- 128 GB DDR4 2933。
- 4 TB M.2。
- 昇腾 Atlas 300I A2 64 GB × 1。
- 1250 W ATX 电源。
- Qwen3-30B-A3B，首版按 W8A8 量化版本验证。

预测维护解释层允许使用 Qwen3-14B 或经过压测的等价模型；Qwen3-30B-A3B 仍是目标模型和智能助手主模型。具体上下文长度、并发数、首 token 延迟和 token/s 目标由业务方确认，并通过实机压测固化。单卡容量不足以支持 30B 模型 BF16 生产部署。

主服务器与算力服应使用独立主机资源。算力服旁路压测时，主服务器的用户请求、图表查询、工单处理和既有定时任务仍需满足各自的基线指标。

### 7.4 离线和国产化

- 系统应支持隔离网络部署，不依赖公网服务。
- 镜像、模型、embedding 模型、rerank 模型、知识语料和依赖应支持离线导入与版本校验。
- 关系库、向量库、对象存储和应用运行时应在 ARM64 环境完成兼容性验证。

### 7.5 可维护性与可观测性

- RAG 知识包应支持版本发布、校验、回滚和问题定位。
- 运维应能查看模型、embedding、rerank、向量库和索引版本的可用性。
- 应记录 MQTT 发布与消费延迟、积压、幂等命中、水位等待、历史查询、规则集版本、动作库版本、规则命中、模型解释、模板回退、结果校验和建单等关键阶段的耗时与错误。

## 8. 验收标准

### 8.1 预测性维护

- 预测维护页直接进入待确认事件列表，不展示全站健康概览，并支持按站点和设备类型进行结构化组合筛选。
- 事件风险状态能按“数据不足、需关注、建议检修”三类正确展示，不出现正常状态。
- 主服务器能按配置周期调用探测器和备电分析，并使用 MQTT 同步的近期数据输出风险等级、关键依据、建议动作和条件数据限制。
- 数据不足、设备不存在和权限不足时返回明确结果。
- `watch`、`inspect` 能自动生成内部工单，`insufficient_data` 不生成异常工单。
- 同一设备、同一风险类型在 24 小时抑制窗口内只保留一张有效工单，重复结果更新已有分析。
- 算力服宕机、超时、返回无效 JSON 或 MQTT 中断时，主服务器其他业务正常，且不生成异常工单。
- 解释模型超时或返回无效内容时，只要规则分析结果有效，系统仍通过模板解释发布事件，并记录 `explanation_source=template`。
- 用户能对事件提交一次“准确”或“需修正”的人工审核结论并归档；归档后事件进入已确认记录，AI 评价标签由审核结论派生。
- 人工审核只产生一份审核记录，不再生成相互独立的工单确认记录和 AI 评价记录。
- 事件详情采用当前 1080px 设计宽度，并保持数据面板、右侧审核栏和响应式行为与现有实现一致；只有 AI 综合分析区域内部简化为综合判断、关键依据、建议动作和条件数据限制。
- AI 区域最多展示 3 条关键依据和 3 条建议动作，不展示旧的支持证据、数据缺口、后续复核、维护建议四个独立卡片，也不展示置信度或模型精度。
- `insufficient_data` 事件不调用解释模型，不展示由维护规则或动作库派生的普通维护建议，只展示数据不足原因、缺失项和补数条件；既有设备告警事件可保留告警状态保持和现场核查提示，但不得新增独立建议动作。
- 预测维护页面统一使用“事件”“新事件分析”和“已确认记录”等术语；已确认记录列表标题使用“已确认事件记录”。
- 自动分析结果不能触发任何设备操作、报警确认或外部 MES 工单流转。

### 8.2 智能助手与 RAG

- 助手能区分知识问答、设备状态查询和报告请求。
- 事实性回答经过召回和 rerank，并包含可定位引用。
- 知识无命中时明确返回无依据结果，不编造引用。
- 固定知识包可以离线构建、校验、原子切换和回滚。
- 单次查询不会混用新旧知识版本。
- embedding、rerank 或向量库不可用时返回明确错误或已批准的降级结果。

### 8.3 安全与可运维性

- 用户端无法直接访问算力服内部模型、embedding、rerank 或向量库。
- 无有效服务令牌或来源非法的请求被拒绝并记录审计。
- 算力服无法直接访问主服务器数据库，历史查询接口只返回去标识化数据。
- MQTT 重复、乱序和积压不会产生重复记录，也不会让算力服使用未达到请求水位的数据生成正式结论。
- 算力服旁路故障或高负载不会阻塞主服务器鉴权、图表、工单和其他定时任务。
- 用户端和主服务器接口中不存在知识文档上传、删除、审核或索引管理入口。
- 系统能够在隔离网络完成启动、知识发布、健康检查和故障恢复。

## 9. 依赖与待确认事项

| 类别 | 待确认内容 | 影响 |
| --- | --- | --- |
| 外部接口 | 主服务器分析调用接口、历史查询接口、MQTT 主题与消息契约、服务令牌轮换 | 决定联调时间与数据可用性 |
| 硬件 | CANN、NPU 驱动、鲲鹏平台版本和磁盘冗余方案 | 决定镜像、设备挂载和可靠性 |
| 模型容量 | 30B 目标模型及 14B 解释模型在单卡下的上下文、并发、延迟和吞吐 | 决定预测维护解释模型选择及是否需要增加推理卡 |
| 知识范围 | 固定语料范围、版本频率、密级和权限规则 | 决定知识包和检索过滤条件 |
| RAG 部署 | embedding/rerank 使用 CPU 还是 NPU | 决定内存/显存配额和检索延迟 |
| 数据库 | 主服务器关系库、算力服时序库、向量库和对象存储的具体产品与版本 | 决定兼容性、备份和索引发布方案 |
| 数据规则 | 数采频率、MQTT 同步时效、异常阈值、规则集、动作库、抑制窗口和历史窗口 | 决定维护分析的准确性、时效和可维护性 |
| 报表 | 报告格式、模板、存储期限和下载权限 | 决定报告生成和存储方案 |

## 10. 里程碑

| 阶段 | 目标 |
| --- | --- |
| M0：需求与接口确认 | 固化业务范围、主服务器边界、模拟数据和最小端到端链路 |
